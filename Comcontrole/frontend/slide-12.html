Estados de UI, skeleton loaders e máquina de estados
Toda operação de IA tem exatamente 3 estados — modele todos

O erro mais comum em interfaces de IA: modelar apenas o estado de sucesso. Quando a API demora 5 segundos ou retorna um erro, a interface fica em branco ou quebrada. Toda operação assíncrona deve modelar explicitamente: idle, loading, success e error.

EstadoO que o usuário vêComponente ReactArmadilha comum
IdleEstado inicial — nenhuma operação em cursoPlaceholder, input habilitadoMostrar mensagem de "sem dados" quando na verdade ainda não carregou
LoadingSkeleton loader ou spinner — algo está acontecendoSkeleton, disabled inputsUsar spinner genérico em vez de skeleton do shape do conteúdo
SuccessConteúdo real renderizadoComponente de conteúdoNão limpar o estado de loading antes de renderizar o conteúdo
ErrorMensagem clara + ação de retryErrorState com botãoMostrar erros técnicos ("TypeError: Cannot read...") para o usuário
useReducer para máquinas de estado complexas: quando um componente tem múltiplas transições de estado relacionadas (loading→error, loading→success, error→loading via retry), useReducer é mais legível e seguro do que múltiplos useState. Garante que estados impossíveis (loading=true AND error=true) nunca existam.
React — máquina de estados com useReducer
// Estado tipado — impossível ter loading + error ao mesmo tempo
const estadoInicial = { status: 'idle', dados: null, erro: null };

function reducer(estado, acao) {
  switch (acao.tipo) {
    case 'CARREGAR':
      return { status: 'loading', dados: null,       erro: null };
    case 'SUCESSO':
      return { status: 'success', dados: acao.dados,  erro: null };
    case 'ERRO':
      return { status: 'error',   dados: null,       erro: acao.erro };
    default:
      return estado;
  }
}

function PainelIA() {
  const [estado, dispatch] = useReducer(reducer, estadoInicial);

  async function buscarResposta(pergunta) {
    dispatch({ tipo: 'CARREGAR' });
    try {
      const dados = await chamarAPI(pergunta);
      dispatch({ tipo: 'SUCESSO', dados });
    } catch (e) {
      dispatch({ tipo: 'ERRO', erro: traduzirErro(e) }); // nunca expõe e.message bruto
    }
  }

  return (
    <div>
      {estado.status === 'idle'    && <Placeholder />}
      {estado.status === 'loading' && <SkeletonResposta />}
      {estado.status === 'success' && <Resposta dados={estado.dados} />}
      {estado.status === 'error'   && <EstadoErro erro={estado.erro} onRetry={() => buscarResposta(ultimaPergunta)} />}
    </div>
  );
}
Skeleton loaders — por que são superiores a spinners

Um spinner diz "aguarde". Um skeleton diz "aqui vem uma resposta com esse tamanho e formato". O skeleton reduz a percepção de espera porque o usuário pode antecipar onde o conteúdo vai aparecer — os olhos já se posicionam. Em interfaces de IA onde as respostas têm forma previsível (bubble de chat, card de resultado), sempre prefira skeleton.

❌ Spinner genérico

Não informa nada sobre o que está carregando nem quanto tempo vai demorar.

✅ Skeleton da bubble de chat

O usuário sabe que virá uma resposta em texto com esse tamanho aproximado.

🙋 Por que usar useReducer em vez de vários useState para modelar os estados de uma requisição de IA?
A
useReducer é mais rápido — o React re-renderiza menos vezes ao atualizar um único objeto de estado
B
useReducer centraliza as transições e impede estados impossíveis — é impossível ter loading=true e error=true ao mesmo tempo quando o estado é um único objeto
C
useState não suporta objetos — apenas primitivos como strings e números
D
É apenas uma convenção de código — os dois produzem exatamente o mesmo resultado

Erros úteis, transparência e feedback do usuário
Mensagens de erro que ajudam vs mensagens que assustam

Erros em interfaces de IA são frequentes: timeout, rate limit, modelo indisponível, contexto muito longo, resposta filtrada por conteúdo. A diferença entre uma boa e má UX está em traduzir o erro técnico em uma ação clara para o usuário.

Antes — erro técnico exposto
TypeError: Failed to fetch
Error: Request failed with status code 429. RateLimitError: You exceeded your current quota, please check your plan and billing details.

O usuário não sabe o que é "quota", "status 429" nem como resolver. Parece que o app quebrou.

Depois — erro traduzido e acionável
Muitas mensagens em pouco tempo
O serviço de IA está ocupado agora. Aguarde alguns segundos e tente novamente.

O usuário entende o problema e tem uma ação clara. A interface não parece quebrada.

JavaScript — traduzirErro.js
/**
 * Converte erros técnicos em mensagens amigáveis com ação sugerida
 * Nunca expõe stack traces ou mensagens de erro internas ao usuário
 */
export function traduzirErro(erro) {
  // Erros HTTP da OpenAI/HuggingFace
  if (erro.status === 429 || erro.message?.includes('rate limit')) {
    return {
      icone: 'clock', cor: 'yellow',
      titulo: 'Muitas mensagens em pouco tempo',
      descricao: 'O serviço de IA está ocupado agora. Aguarde alguns segundos.',
      acao: 'retry', tempoEspera: 5000,
    };
  }
  if (erro.status === 401 || erro.message?.includes('API key')) {
    return {
      icone: 'key', cor: 'red',
      titulo: 'Problema de autenticação',
      descricao: 'Houve um problema com as credenciais. Entre em contato com o suporte.',
      acao: 'none',
    };
  }
  if (erro.status === 400 || erro.message?.includes('context length')) {
    return {
      icone: 'scissors', cor: 'orange',
      titulo: 'Conversa muito longa',
      descricao: 'A conversa ficou longa demais. Inicie uma nova conversa para continuar.',
      acao: 'new-chat',
    };
  }
  if (erro.name === 'AbortError') {
    return null; // cancelamento intencional — sem erro para o usuário
  }
  // Erro de rede (offline, timeout)
  if (!navigator.onLine || erro.message?.includes('fetch')) {
    return {
      icone: 'wifi-slash', cor: 'red',
      titulo: 'Sem conexão com a internet',
      descricao: 'Verifique sua conexão e tente novamente.',
      acao: 'retry',
    };
  }
  // Fallback genérico — nunca expõe o erro bruto
  return {
    icone: 'exclamation-triangle', cor: 'red',
    titulo: 'Algo deu errado',
    descricao: 'Não foi possível gerar uma resposta agora. Tente novamente em instantes.',
    acao: 'retry',
  };
}
Transparência e confiança — o que mostrar sobre a IA

Interfaces de IA que fingem ser perfeitas constroem desconfiança quando erram. Interfaces que comunicam limitações proativamente fazem o usuário usar o produto com mais inteligência — e confiar mais quando ele acerta.

Padrões de transparência — aplicar no chatbot
📅
Data de corte do conhecimento
"Meu conhecimento vai até [data]. Para eventos mais recentes, verifique outras fontes." — Exiba quando detectar perguntas sobre eventos atuais (palavras-chave: "hoje", "agora", "recentemente", ano atual).
Fácil
⚠️
Aviso para tópicos críticos
"Para decisões médicas, jurídicas ou financeiras, consulte um profissional habilitado." — Detecte keywords (ex: "medicamento", "contrato", "investir") e adicione o disclaimer automaticamente.
Médio
🎯
Indicador de confiança do modelo
Para modelos de classificação (sentimento, NER), exiba o score de confiança junto ao resultado: "Sentimento: Positivo (92% confiança)". Scores abaixo de 70% merecem um aviso explícito: "Resultado incerto — leia com atenção."
Médio
✏️
Permitir edição e confirmação
Para ações consequentes (enviar e-mail, deletar arquivo, fazer compra), sempre mostre um preview editável antes de executar. "A IA vai enviar: [preview]. Confirmar?" — Nunca execute ações irreversíveis sem confirmação humana explícita.

C

D

Passo a passo do LAB
1
Migrar useState para useReducer
Substitua os múltiplos estados de loading/erro do chatbot por um único useReducer com ações CARREGAR, SUCESSO, ERRO e TOKEN (para streaming). Garanta que é impossível ter estados contraditórios.
2
Substituir "gerando..." por SkeletonBubble
Quando o stream ainda não iniciou (requisição em voo mas nenhum token chegou), exiba o SkeletonBubble. Quando o primeiro token chegar, troque automaticamente para a bubble de texto crescente com cursor piscante.
3
Adicionar tratamento de erro com retry
Envolva o stream em try/catch e use traduzirErro(). No estado de erro, exiba o componente EstadoErro com o botão "Tentar novamente" que reenvia a última mensagem do usuário automaticamente.
4
Implementar thumbs up/down
Cada mensagem do assistente tem um par de botões 👍/👎. O feedback é salvo em localStorage com o id da mensagem. Persiste ao recarregar a página. Em produção, esse dado seria enviado a um endpoint de analytics para fine-tuning.
5
Disclaimer automático e aviso de contexto longo
Detecte palavras-chave na resposta (médico, lei, contrato, investimento) e adicione o disclaimer abaixo da mensagem. Conte os tokens aproximados do histórico (palavras × 1.3) e exiba um banner quando ultrapassar 80% do limite do modelo (ex: 3.200 de 4.096 tokens).
React — componentes de feedback e disclaimer
import { useState, useEffect } from 'react';

/* ── Thumbs up/down por mensagem ── */
function FeedbackBotoes({ msgId }) {
  const [voto, setVoto] = useState(
    () => localStorage.getItem(`feedback:${msgId}`) || null
  );

  function votar(valor) {
    const novo = voto === valor ? null : valor; // toggle
    setVoto(novo);
    if (novo) localStorage.setItem(`feedback:${msgId}`, novo);
    else       localStorage.removeItem(`feedback:${msgId}`);
    // Em produção: await fetch('/api/feedback', { method:'POST', body: JSON.stringify({ msgId, voto: novo }) });
  }

  return (
    <div className="feedback-botoes" aria-label="Avaliar resposta">
      <button
        className={`btn-thumb ${voto === 'up' ? 'ativo' : ''}`}
        onClick={() => votar('up')}
        aria-label="Resposta útil"
        title="Resposta útil"
      >
        {voto === 'up' ? '👍' : '👍'}
      </button>
      <button
        className={`btn-thumb ${voto === 'down' ? 'ativo' : ''}`}
        onClick={() => votar('down')}
        aria-label="Resposta não útil"
        title="Resposta não útil"
      >
        {voto === 'down' ? '👎' : '👎'}
      </button>
    </div>
  );
}

/* ── Disclaimer para tópicos críticos ── */
const PALAVRAS_CRITICAS = [
  'médico', 'doença', 'remédio', 'diagnóstico', 'tratamento',
  'advogado', 'contrato', 'lei', 'processo',
  'investir', 'ação', 'financeiro', 'imposto',
];

function precisaDisclaimer(texto) {
  const lower = texto.toLowerCase();
  return PALAVRAS_CRITICAS.some(p => lower.includes(p));
}

function Disclaimer() {
  return (
    <div className="disclaimer" role="note">
      <i className="fas fa-info-circle" />
      <span>
        Esta resposta é informativa. Para decisões médicas, jurídicas ou financeiras,
        consulte um profissional habilitado.
      </span>
    </div>
  );
}

/* ── Aviso de contexto longo ── */
function estimarTokens(historico) {
  return historico
    .reduce((acc, m) => acc + m.content.split(/\s+/).length, 0) * 1.3;
}

function AvisoContextoLongo({ historico, limite = 4096 }) {
  const estimativa = estimarTokens(historico);
  const pct = (estimativa / limite) * 100;
  if (pct < 80) return null;
  return (
    <div className="aviso-contexto" role="alert">
      <i className="fas fa-memory" />
      <span>
        Conversa usando ~{pct.toFixed(0)}% do contexto disponível.
        {pct >= 95 ? ' Inicie uma nova conversa para continuar com qualidade.' : ' Considere iniciar uma nova conversa em breve.'}
      </span>
    </div>
  );
}

/* ── Usando tudo junto no historico do chat ── */
{historico.map((m, i) => (
  <div key={m.id || i}>
    <div className={`bubble bubble--${m.role}`}>
      <span className="bubble__label">{m.role === 'user' ? 'Você' : 'IA'}</span>

        <FeedbackBotoes msgId={m.id || i} />

Exercício 02 — Retry automático com backoff

Implemente a lógica de retry automático no componente EstadoErro: quando o erro for do tipo "rate limit" (status 429), aguarde tempoEspera segundos e tente novamente automaticamente. Mostre um contador regressivo: "Tentando novamente em 5..." → 4 → 3 → 2 → 1 → retry. Permita que o usuário cancele o retry automático clicando em "Cancelar".

LAB
React — EstadoErro com retry automático
function EstadoErro({ erro, onRetry }) {
  const [contador, setContador] = useState(
    erro.tempoEspera ? erro.tempoEspera / 1000 : null
  );

  useEffect(() => {
    if (!contador) return;
    if (contador <= 0) { onRetry(); return; }
    const id = setInterval(() => setContador(c => c - 1), 1000);
    return () => clearInterval(id);
  }, [contador]);

  return (
    <div className="estado-erro">
      <p>{erro.titulo}</p>
      <p>{erro.descricao}</p>
      {contador !== null && <p>Tentando novamente em {contador}...</p>}
      <div>
        <button onClick={onRetry}>Tentar agora</button>
        <button onClick={() => setContador(null)}>Cancelar</button>
      </div>
    </div>
  );
}
Exercício 03 — Error Boundary para erros inesperados

React Error Boundaries capturam erros de renderização que escapam do try/catch — como um modelo retornar dados em formato inesperado que quebra o MarkdownRenderer. Implemente um ErrorBoundary como componente de classe (obrigatório para usar componentDidCatch) que envolve o chat e exibe uma UI amigável com botão para recarregar. Em quais situações um Error Boundary é necessário que um try/catch não cobre?

Conceito + código
React — ErrorBoundary.jsx
import { Component } from 'react';

export class ErrorBoundary extends Component {
  constructor(props) {
    super(props);
    this.state = { temErro: false, mensagem: '' };
  }

  static getDerivedStateFromError(erro) {
    return { temErro: true, mensagem: erro.message };
  }

  componentDidCatch(erro, info) {
    // Em produção: enviar para Sentry, Datadog, etc.
    console.error('ErrorBoundary capturou:', erro, info);
  }

  render() {
    if (this.state.temErro) {
      return (
        <div style={{ padding: '2rem', textAlign: 'center' }}>
          <p>😵 Algo inesperado aconteceu.</p>
          <button onClick={() => { this.setState({ temErro: false }); window.location.reload(); }}>
            Recarregar
          </button>
        </div>
      );
    }
    return this.props.children;
  }
}

// Uso: <ErrorBoundary><ChatbotStream /></ErrorBoundary>

// Por que try/catch não é suficiente?
// try/catch captura erros em código imperativo (async/await).
// Error Boundary captura erros durante a fase de RENDERIZAÇÃO do React —
// quando um componente filho lança um erro ao retornar JSX.
// Exemplo: MarkdownRenderer recebe null.replace() → quebra no render.
// Esse erro NÃO é capturado por try/catch em useEffect ou event handlers.
