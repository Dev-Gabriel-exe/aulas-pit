Os limites da Context API e por que apps de IA precisam de mais
O que a Context API resolve — e o que ela não resolve bem

Desde a Semana 3, você usa Context API para evitar prop drilling — passar um estado por vários níveis de componentes que não precisam dele. Isso funciona bem para dados que mudam pouco (tema, usuário logado, idioma). Mas em um chatbot de IA real, o estado muda o tempo todo: cada token que chega no streaming, cada troca de conversa, cada configuração de modelo.

O problema: todo componente que consome um Context re-renderiza sempre que qualquer parte do valor do Context muda — mesmo que o componente só use uma fatia pequena dele. Se o seu ChatContext guarda { mensagens, modeloAtivo, tema, listaConversas }, um componente que só lê tema vai re-renderizar a cada novo token de streaming.

A regra prática: Context API é ótimo para estado que muda raramente e é lido por muitos componentes (tema, autenticação). Para estado que muda com frequência alta (streaming, listas de mensagens, formulários complexos) ou que precisa de seletores granulares (ler só uma fatia sem re-renderizar por causa de outra), uma store dedicada como Zustand ou Redux Toolkit resolve melhor.
React — o problema do re-render em cascata com Context
// ChatContext guarda tudo junto — qualquer mudança re-renderiza todo mundo
const ChatContext = createContext();

function ChatProvider({ children }) {
  const [mensagens, setMensagens] = useState([]);
  const [modeloAtivo, setModeloAtivo] = useState('gpt-4o-mini');
  const [tema, setTema] = useState('escuro');

  // Um único objeto de valor — cada streaming de token recria isso inteiro
  const valor = { mensagens, setMensagens, modeloAtivo, setModeloAtivo, tema, setTema };

  return <ChatContext.Provider value={valor}>{children}</ChatContext.Provider>;
}

// Este componente só lê "tema", mas re-renderiza a cada token de streaming
// porque "valor" é um objeto novo a cada render do Provider
function BotaoTema() {
  const { tema, setTema } = useContext(ChatContext);
  return <button onClick={() => setTema(t => t === 'escuro' ? 'claro' : 'escuro')}>{tema}</button>;
}
Zustand — a store mínima que resolve isso sem boilerplate

Zustand ("estado" em alemão) é uma biblioteca de gerenciamento de estado que resolve o problema de re-render seletivamente: cada componente escolhe exatamente qual fatia do estado quer ler, e só re-renderiza quando aquela fatia muda. Não precisa de Provider envolvendo a árvore, não precisa de reducers verbosos — é uma função que cria um hook.

React — primeira store Zustand para o chatbot
// store/useChatStore.js
import { create } from 'zustand';

export const useChatStore = create((set, get) => ({
  // Estado
  mensagens: [],
  modeloAtivo: 'gpt-4o-mini',
  tema: 'escuro',

  // Ações — funções que modificam o estado, vivem no mesmo lugar
  adicionarMensagem: (msg) => set((estado) => ({
    mensagens: [...estado.mensagens, msg]
  })),

  definirModelo: (modelo) => set({ modeloAtivo: modelo }),

  alternarTema: () => set((estado) => ({
    tema: estado.tema === 'escuro' ? 'claro' : 'escuro'
  })),

  limparConversa: () => set({ mensagens: [] }),
}));

// ── Uso em qualquer componente, sem Provider ──

// Este componente SÓ re-renderiza quando "tema" muda —
// não é afetado por novas mensagens chegando via streaming
function BotaoTema() {
  const tema = useChatStore((estado) => estado.tema);
  const alternarTema = useChatStore((estado) => estado.alternarTema);
  return <button onClick={alternarTema}>{tema}</button>;
}

// Este componente só re-renderiza quando "mensagens" muda
function ListaMensagens() {
  const mensagens = useChatStore((estado) => estado.mensagens);
  return mensagens.map(m => <Bubble key={m.id} msg={m} />);
}
O segredo da seletividade: useChatStore((estado) => estado.tema) passa um seletor — uma função que extrai só a fatia que o componente precisa. O Zustand compara o valor retornado entre renders e só dispara re-render se ele mudou. É por isso que BotaoTema ignora completamente as mudanças em mensagens.
🙋 Um componente Sidebar lê apenas useChatStore(estado => estado.modeloAtivo). Uma nova mensagem chega via streaming e é adicionada ao array de mensagens na store. O que acontece com a Sidebar?
A
A Sidebar re-renderiza, pois qualquer mudança na store afeta todos os componentes que a usam
B
A Sidebar NÃO re-renderiza, porque o seletor só observa modeloAtivo, que não mudou
C
A Sidebar lança um erro, pois duas partes da store não podem mudar de forma independente
D
Depende de haver um Provider envolvendo a Sidebar — sem ele, o valor fica desatualizado

Zustand avançado — slices, middleware persist e devtools
Organizando a store em slices

Conforme o app cresce, uma única store com dezenas de campos fica difícil de navegar. O padrão de slices divide a store em fatias temáticas (chat, configurações, UI) que são combinadas em uma store única — mantendo a simplicidade do Zustand mas com organização de código clara.

JavaScript — store dividida em slices
// slices/chatSlice.js
export const criarChatSlice = (set, get) => ({
  mensagens: [],
  streaming: false,
  adicionarMensagem: (msg) => set((estado) => ({ mensagens: [...estado.mensagens, msg] })),
  setStreaming: (valor) => set({ streaming: valor }),
});

// slices/configSlice.js
export const criarConfigSlice = (set, get) => ({
  modeloAtivo: 'gpt-4o-mini',
  temperatura: 0.7,
  definirModelo: (modelo) => set({ modeloAtivo: modelo }),
  definirTemperatura: (t) => set({ temperatura: t }),
});

// store/useAppStore.js — combina os slices em uma única store
import { create } from 'zustand';
import { criarChatSlice } from '../slices/chatSlice';
import { criarConfigSlice } from '../slices/configSlice';

export const useAppStore = create((...a) => ({
  ...criarChatSlice(...a),
  ...criarConfigSlice(...a),
}));

// Uso — continua sendo um único hook, componentes não sabem que é dividido em slices
const streaming = useAppStore((e) => e.streaming);
const modeloAtivo = useAppStore((e) => e.modeloAtivo);
Middleware persist — salvando a store no localStorage automaticamente

O middleware persist envolve a store e sincroniza automaticamente com localStorage (ou outra engine de storage) a cada mudança. É exatamente o que resolve o problema de perder o histórico de conversa ao recarregar a página.

JavaScript — store com persist e partialize
import { create } from 'zustand';
import { persist, createJSONStorage } from 'zustand/middleware';

export const useChatStore = create(
  persist(
    (set, get) => ({
      conversas: [],           // [{ id, titulo, mensagens: [...] }]
      conversaAtivaId: null,
      streaming: false,       // NÃO deve ser persistido — é estado transitório

      novaConversa: () => set((estado) => {
        const nova = { id: crypto.randomUUID(), titulo: 'Nova conversa', mensagens: [] };
        return { conversas: [nova, ...estado.conversas], conversaAtivaId: nova.id };
      }),

      adicionarMensagem: (msg) => set((estado) => ({
        conversas: estado.conversas.map(c =>
          c.id === estado.conversaAtivaId
            ? { ...c, mensagens: [...c.mensagens, msg] }
            : c
        )
      })),
    }),
    {
      name: 'chatbot-storage',               // chave usada no localStorage
      storage: createJSONStorage(() => localStorage),
      // partialize escolhe o que É salvo — exclui campos transitórios como "streaming"
      partialize: (estado) => ({
        conversas: estado.conversas,
        conversaAtivaId: estado.conversaAtivaId,
      }),
    }
  )
);

// Ao recarregar a página, o Zustand automaticamente reidrata o estado
// a partir do localStorage antes do primeiro render — sem código extra.
Por que usar partialize: nem tudo na store deve ir para o localStorage. Estados transitórios como streaming: true/false ou uma referência a um AbortController não fazem sentido persistidos — se o usuário recarrega no meio de um streaming, ele não estava realmente "streamando" mais. partialize evita salvar lixo e mantém o localStorage enxuto.
🙋 Por que o campo streaming foi excluído no partialize do exemplo acima?
A
Porque booleans não podem ser serializados em JSON
B
Porque é um estado transitório da sessão atual — persistir "streaming: true" faria a UI achar que ainda está gerando uma resposta após recarregar, quando na verdade a conexão foi perdida
C
Porque o localStorage tem um limite de tamanho e esse campo ocuparia espaço demais
D
Não há motivo técnico — foi apenas uma escolha estética do exemplo

Redux Toolkit — quando a complexidade do projeto pede mais estrutura
Redux Toolkit — createSlice e configureStore

Redux existe há mais tempo que Zustand e é usado em bases de código grandes, times maiores e projetos com regras de negócio complexas envolvendo estado. O Redux Toolkit (RTK) é a forma moderna e recomendada de usar Redux — elimina o boilerplate do Redux clássico (action types, action creators e reducers separados) através de createSlice.

JavaScript — slice e store com Redux Toolkit
// features/chatSlice.js
import { createSlice } from '@reduxjs/toolkit';

const chatSlice = createSlice({
  name: 'chat',
  initialState: {
    mensagens: [],
    modeloAtivo: 'gpt-4o-mini',
  },
  reducers: {
    // RTK usa Immer por baixo dos panos — parece que você está "mutando"
    // o estado diretamente, mas na verdade produz um novo estado imutável
    mensagemAdicionada(estado, acao) {
      estado.mensagens.push(acao.payload);   // "mutação" segura via Immer
    },
    modeloDefinido(estado, acao) {
      estado.modeloAtivo = acao.payload;
    },
    conversaLimpa(estado) {
      estado.mensagens = [];
    },
  },
});

// Actions são geradas automaticamente a partir dos nomes dos reducers
export const { mensagemAdicionada, modeloDefinido, conversaLimpa } = chatSlice.actions;
export default chatSlice.reducer;

// store/index.js
import { configureStore } from '@reduxjs/toolkit';
import chatReducer from '../features/chatSlice';

export const store = configureStore({
  reducer: { chat: chatReducer },
  // configureStore já vem com Redux DevTools e middleware de checagem habilitados
});

// main.jsx — Redux PRECISA de um Provider envolvendo a árvore
import { Provider } from 'react-redux';
<Provider store={store}>
  <App />
</Provider>

// Uso em um componente — useSelector lê, useDispatch escreve
import { useSelector, useDispatch } from 'react-redux';
import { mensagemAdicionada } from '../features/chatSlice';

function CampoInput() {
  const dispatch = useDispatch();
  const mensagens = useSelector((estado) => estado.chat.mensagens);

  function enviar(texto) {
    dispatch(mensagemAdicionada({ id: crypto.randomUUID(), role: 'user', content: texto }));
  }
  // ...
}
Immer por baixo dos panos: em Redux clássico, mutar o estado diretamente (estado.mensagens.push(...)) é proibido e quebra a previsibilidade do Redux. O RTK usa a biblioteca Immer internamente: dentro de um reducer do createSlice, você escreve como se estivesse mutando, mas o Immer produz um novo objeto imutável por trás. Isso elimina o erro mais comum do Redux clássico (retornar um novo objeto manualmente com spread em cada campo).
Zustand vs Redux Toolkit — qual escolher
Zustand
  • ~1KB, zero boilerplate, sem Provider
  • Ótimo para projetos pequenos e médios, MVPs, protótipos de IA
  • Curva de aprendizado mínima — é só um hook
  • Menos convenções impostas — pode gerar inconsistência em times grandes sem disciplina própria
  • DevTools e persist via middleware opcional
Redux Toolkit
  • Mais estrutura e convenções — bom para times grandes e projetos de longa duração
  • Redux DevTools nativo e maduro — time-travel debugging
  • Ecossistema extenso (RTK Query para cache de API, middleware customizado)
  • Exige Provider, mais conceitos (actions, reducers, slices, store)
  • Mais verboso para casos simples — pode ser "demais" para um app pequeno
Regra prática para projetos de IA: se o app tem uma store relativamente simples (histórico de chat, configurações, tema), Zustand é a escolha mais rápida e com menos atrito. Se o projeto já usa Redux em outras partes, tem uma equipe grande, ou precisa de ferramentas avançadas como RTK Query para cache de chamadas de API, Redux Toolkit compensa o boilerplate extra. Para a maioria dos projetos acadêmicos e MVPs desta disciplina, Zustand é suficiente e mais produtivo.
🙋 Um estudante mistura mutação direta de estado dentro de um reducer criado com createSlice do Redux Toolkit: estado.mensagens.push(msg). Isso quebra o app?
A
Sim — Redux nunca permite mutação, isso lança uma exceção imediatamente em qualquer versão
B
Não — dentro de reducers do createSlice, o RTK usa Immer, que permite essa sintaxe de "mutação" e converte para uma atualização imutável automaticamente
C
Só funciona se o array já existir e tiver pelo menos um item
D
Funciona igual em Redux clássico e RTK — mutação sempre foi permitida em reducers

React — store final com múltiplas conversas e devtools
import { create } from 'zustand';
import { persist, createJSONStorage, devtools } from 'zustand/middleware';

export const useChatStore = create(
  devtools(
    persist(
      (set, get) => ({
        conversas: [],
        conversaAtivaId: null,
        streaming: false,

        novaConversa: () => set((estado) => {
          const nova = { id: crypto.randomUUID(), titulo: 'Nova conversa', mensagens: [] };
          return { conversas: [nova, ...estado.conversas], conversaAtivaId: nova.id };
        }, false, 'chat/novaConversa'),  // terceiro argumento = nome da ação no DevTools

        selecionarConversa: (id) => set({ conversaAtivaId: id }, false, 'chat/selecionarConversa'),

        adicionarMensagem: (msg) => set((estado) => ({
          conversas: estado.conversas.map(c =>
            c.id === estado.conversaAtivaId ? { ...c, mensagens: [...c.mensagens, msg] } : c
          )
        }), false, 'chat/adicionarMensagem'),

        excluirConversa: (id) => set((estado) => ({
          conversas: estado.conversas.filter(c => c.id !== id),
          conversaAtivaId: estado.conversaAtivaId === id ? null : estado.conversaAtivaId,
        }), false, 'chat/excluirConversa'),
      }),
      {
        name: 'chatbot-storage',
        storage: createJSONStorage(() => localStorage),
        partialize: (estado) => ({ conversas: estado.conversas, conversaAtivaId: estado.conversaAtivaId }),
      }
    ),
    { name: 'ChatStore' }  // nome que aparece no Redux DevTools
  )
);

Exercício 01 — Seletor derivado com useMemo/shallow

Um componente ContadorMensagens precisa exibir quantas mensagens tem a conversa ativa. Escreva o seletor que combina conversas e conversaAtivaId para retornar apenas o número, evitando re-renderizar quando outras conversas mudam. Use useShallow de zustand/react/shallow se o seletor retornar um objeto/array.

LAB
React — seletor derivado eficiente
function ContadorMensagens() {
  // Seletor derivado — retorna só um número primitivo
  // re-renderiza apenas quando esse número muda, não a cada mudança em "conversas"
  const total = useChatStore((estado) => {
    const ativa = estado.conversas.find(c => c.id === estado.conversaAtivaId);
    return ativa ? ativa.mensagens.length : 0;
  });

  return <span>{total} mensagens</span>;
}

// Se precisar retornar um objeto/array do seletor (ex: as últimas 3 mensagens),
// use useShallow para comparar por igualdade rasa em vez de referência:
import { useShallow } from 'zustand/react/shallow';

const ultimasTres = useChatStore(
  useShallow((estado) => {
    const ativa = estado.conversas.find(c => c.id === estado.conversaAtivaId);
    return ativa ? ativa.mensagens.slice(-3) : [];
  })
);
Exercício 02 — Exportar e importar conversas em JSON

Adicione duas ações à store: exportarConversas() que gera um Blob JSON de todas as conversas e dispara o download via URL.createObjectURL, e importarConversas(arquivo) que lê um arquivo JSON selecionado pelo usuário (via input type="file") e mescla as conversas na store, evitando ids duplicados.

LAB
JavaScript — exportar/importar conversas
// Ações adicionadas à store
exportarConversas: () => {
  const { conversas } = get();
  const blob = new Blob([JSON.stringify(conversas, null, 2)], { type: 'application/json' });
  const url = URL.createObjectURL(blob);
  const a = document.createElement('a');
  a.href = url;
  a.download = `conversas-${Date.now()}.json`;
  a.click();
  URL.revokeObjectURL(url);
},

importarConversas: async (arquivo) => {
  const texto = await arquivo.text();
  const novasConversas = JSON.parse(texto);
  set((estado) => {
    const idsExistentes = new Set(estado.conversas.map(c => c.id));
    const semDuplicar = novasConversas.filter(c => !idsExistentes.has(c.id));
    return { conversas: [...semDuplicar, ...estado.conversas] };
  });
},

// Componente — input file disparando a importação
<input
  type="file"
  accept="application/json"
  onChange={(e) => e.target.files[0] && importarConversas(e.target.files[0])}
/>

// features/configSlice.js
import { createSlice } from '@reduxjs/toolkit';

const configSlice = createSlice({

// Leitura
function ModeloAtual() {

function SeletorModelo() {

Exercício 04 — Desafio: migrar para IndexedDB com storage customizado

O localStorage tem limite de ~5-10MB e é síncrono (pode travar a thread para históricos grandes). Implemente um adapter de storage customizado para o middleware persist do Zustand usando IndexedDB (via biblioteca idb-keyval) em vez de localStorage, mantendo a mesma interface esperada pelo createJSONStorage. Explique por que isso é preferível para históricos de conversa muito longos.

Desafio · Storage
JavaScript — storage customizado com IndexedDB
// npm install idb-keyval
import { get, set, del } from 'idb-keyval';
import { persist } from 'zustand/middleware';

// Adapter que implementa a interface StateStorage esperada pelo Zustand:
// getItem, setItem e removeItem, todos podendo retornar Promises
const indexedDBStorage = {
  getItem: async (name) => {
    const valor = await get(name);
    return valor ?? null;
  },
  setItem: async (name, valor) => {
    await set(name, valor);
  },
  removeItem: async (name) => {
    await del(name);
  },
};

 * 1. Limite de armazenamento MUITO maior (centenas de MB a GB, vs ~5-10MB do localStorage)

O que você precisa ter saído daqui dominando
Limites da Context API

Todo consumidor de um Context re-renderiza quando qualquer parte do valor muda. Bom para dados estáveis (tema, auth); ruim para estado de alta frequência (streaming, listas).

Zustand

Store sem Provider, seletores granulares evitam re-render desnecessário. Slices para organização. Middleware persist salva no localStorage/IndexedDB automaticamente.

Redux Toolkit

createSlice + configureStore eliminam o boilerplate do Redux clássico. Immer permite "mutação" segura dentro de reducers. DevTools nativo com time-travel debugging.

Persistência de conversas

partialize escolhe o que é salvo, excluindo estado transitório. Múltiplas conversas com seleção ativa. IndexedDB para históricos grandes além do limite do localStorage.

Checklist final: a store Zustand está sem Provider e os componentes usam seletores granulares? O histórico de conversas sobrevive a um F5? O campo streaming está fora do partialize?
