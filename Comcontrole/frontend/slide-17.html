Por que testar front-end, a pirâmide de testes e primeiros passos com Jest
Por que testar interfaces de IA especificamente

Testar front-end sempre foi importante, mas em apps de IA existe um motivo extra: a camada de IA é lenta, cara e não-determinística. Chamar a API real da OpenAI a cada teste seria lento (segundos por chamada), custaria dinheiro literal a cada execução da suíte, e o texto de retorno muda a cada chamada — impossibilitando um expect(resposta).toBe(...) confiável.

A solução: nunca testar contra a API real. Testes de front-end mockam a chamada de IA e verificam se a interface reage corretamente — mostra o skeleton, renderiza a resposta, trata o erro 429, habilita o botão de retry. O que importa não é o que o modelo disse, é como a UI se comportou.

A pirâmide de testes

A pirâmide de testes descreve a proporção ideal de cada tipo de teste em um projeto saudável: muitos testes unitários rápidos e baratos na base, uma camada média de testes de integração, e poucos testes end-to-end (E2E) no topo — mais lentos e caros de manter.

Testes unitários cobrem a lógica pura (funções auxiliares). E2E fica para poucos fluxos críticos, se houver tempo.
Jest — test, expect e matchers

Jest é o test runner mais usado no ecossistema React: executa arquivos de teste, fornece as funções test/describe para organizar, e expect com matchers para fazer as verificações (assertions).

JavaScript — primeiro teste unitário com Jest
// utils/estimarTokens.js
export function estimarTokens(historico) {
  return historico.reduce((acc, m) => acc + m.content.split(/\s+/).length, 0) * 1.3;
}

// utils/estimarTokens.test.js
import { estimarTokens } from './estimarTokens';

describe('estimarTokens', () => {
  test('retorna 0 para histórico vazio', () => {
    expect(estimarTokens([])).toBe(0);
  });

  test('estima tokens proporcionalmente ao número de palavras', () => {
    const historico = [{ content: 'uma frase com cinco palavras' }]; // 5 palavras
    expect(estimarTokens(historico)).toBeCloseTo(6.5); // 5 * 1.3
  });

  test('soma palavras de múltiplas mensagens', () => {
    const historico = [
      { content: 'oi tudo bem' },      // 3 palavras
      { content: 'sim e você' },       // 3 palavras
    ];
    expect(estimarTokens(historico)).toBeCloseTo(7.8); // 6 * 1.3
  });
});

🙋 Por que os testes de front-end de um chatbot de IA NUNCA devem chamar a API real da OpenAI/HuggingFace durante a execução da suíte?
A
Porque o Jest tecnicamente não consegue fazer chamadas de rede
B
Porque a resposta é não-determinística, a chamada é lenta, custa dinheiro a cada execução e amarra a suíte a uma conexão de rede e a uma API key válida
C
Porque as APIs de IA bloqueiam requisições vindas de ferramentas de teste automatizado
D
Não há problema real nisso — é só uma boa prática opcional sem justificativa técnica forte

React Testing Library — testar comportamento, não implementação
A filosofia da RTL

React Testing Library (RTL) tem uma filosofia declarada: "quanto mais seus testes se parecem com a forma como o software é usado, mais confiança eles te dão". Isso significa: não teste detalhes de implementação (nome de uma variável de estado interna, se um componente usa useState ou useReducer). Teste o que o usuário vê e faz: texto na tela, clique em um botão, o que aparece depois.

Testando implementação (frágil)
Acessar wrapper.state('mensagens') ou wrapper.instance().enviar() diretamente. Quebra a cada refatoração interna, mesmo que o comportamento visível não tenha mudado.
Testando comportamento (resiliente)
Buscar o texto "Enviar" na tela, clicar nele, e verificar que a mensagem do usuário aparece na tela. Continua passando mesmo se você trocar useState por Zustand por dentro.
React — primeiro teste de integração com RTL
import { render, screen } from '@testing-library/react';
import '@testing-library/jest-dom';
import { ChatInput } from './ChatInput';

test('renderiza o campo de mensagem e o botão de enviar', () => {
  render(<ChatInput onEnviar={() => {}} />);

  // getByRole busca pelo papel semântico do elemento — não pelo seletor CSS
  // Isso é exatamente o que um leitor de tela e um usuário enxergam
  const campo = screen.getByRole('textbox', { name: /digite sua mensagem/i });
  const botao = screen.getByRole('button', { name: /enviar/i });

  expect(campo).toBeInTheDocument();
  expect(botao).toBeInTheDocument();
  expect(botao).toBeDisabled(); // campo vazio → botão desabilitado
});
Prioridade de queries da RTL: prefira getByRole (mais próximo do que tecnologia assistiva percebe) > getByLabelText > getByText > getByTestId (último recurso, quando não há forma semântica de encontrar o elemento). Essa hierarquia empurra você a escrever HTML mais acessível — se getByRole falha, geralmente é sinal de falta de aria-label ou semântica correta, não um problema do teste.
user-event — simulando interação real do usuário

A biblioteca @testing-library/user-event simula eventos de forma mais realista que disparar eventos DOM sintéticos diretamente — ela simula a sequência completa de eventos que o browser dispararia (keydown, keypress, input, keyup), incluindo async/await para cada interação.

React — testando digitação e envio com user-event
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { ChatInput } from './ChatInput';

test('habilita o botão ao digitar e chama onEnviar com o texto', async () => {
  const user = userEvent.setup();
  const aoEnviar = jest.fn(); // função mockada — rastreia como foi chamada

  render(<ChatInput onEnviar={aoEnviar} />);

  const campo = screen.getByRole('textbox', { name: /digite sua mensagem/i });
  const botao = screen.getByRole('button', { name: /enviar/i });

  expect(botao).toBeDisabled(); // estado inicial

  await user.type(campo, 'Qual a capital da França?');
  expect(botao).not.toBeDisabled(); // habilitou após digitar

  await user.click(botao);
  expect(aoEnviar).toHaveBeenCalledWith('Qual a capital da França?');
  expect(campo).toHaveValue(''); // campo limpo após enviar
});

test('envia com Enter, mas não com Shift+Enter', async () => {
  const user = userEvent.setup();
  const aoEnviar = jest.fn();
  render(<ChatInput onEnviar={aoEnviar} />);
  const campo = screen.getByRole('textbox');

  await user.type(campo, 'oi{Shift>}{Enter}{/Shift}'); // Shift+Enter = nova linha
  expect(aoEnviar).not.toHaveBeenCalled();

  await user.type(campo, '{Enter}'); // Enter puro = envia
  expect(aoEnviar).toHaveBeenCalled();
});
🙋 Por que a RTL recomenda usar getByRole em vez de getByTestId como primeira opção?
A
getByTestId é mais lento de executar durante a suíte de testes
B
getByRole reflete o que tecnologia assistiva e usuários reais percebem; se a query falha, geralmente revela falta de semântica/acessibilidade no componente, não um problema do teste
C
data-testid não é suportado pelo Jest, apenas pelo Cypress
D
Não há diferença real — é apenas uma preferência estética da equipe da RTL

Mockando chamadas de IA — jest.mock, MSW e streaming simulado
jest.mock — substituindo o módulo de chamada de API

A forma mais direta de mockar é substituir inteiramente o módulo que faz a chamada HTTP por uma versão falsa controlada pelo teste. jest.mock() intercepta o import e injeta uma implementação fake.

React — testando o chatbot com jest.mock
// api/chamarIA.js — módulo real que faz a chamada HTTP
export async function chamarIA(mensagens) {
  const res = await fetch('/api/chat', {
    method: 'POST',
    body: JSON.stringify({ mensagens }),
  });
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
}

// Chatbot.test.jsx
import { render, screen, waitFor } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { Chatbot } from './Chatbot';
import { chamarIA } from './api/chamarIA';

// Substitui TODO o módulo — chamarIA agora é uma função mockada
jest.mock('./api/chamarIA');

test('exibe a resposta da IA após enviar uma mensagem', async () => {
  chamarIA.mockResolvedValue({ content: 'Paris é a capital da França.' });

  const user = userEvent.setup();
  render(<Chatbot />);

  await user.type(screen.getByRole('textbox'), 'Qual a capital da França?{Enter}');

  // waitFor espera a UI se atualizar de forma assíncrona (o "setState" do fetch)
  await waitFor(() => {
    expect(screen.getByText('Paris é a capital da França.')).toBeInTheDocument();
  });

  expect(chamarIA).toHaveBeenCalledWith(
    expect.arrayContaining([expect.objectContaining({ role: 'user', content: 'Qual a capital da França?' })])
  );
});

test('exibe erro amigável quando a API retorna rate limit', async () => {
  chamarIA.mockRejectedValue({ status: 429 });

  const user = userEvent.setup();
  render(<Chatbot />);
  await user.type(screen.getByRole('textbox'), 'oi{Enter}');

  await waitFor(() => {
    expect(screen.getByText(/muitas mensagens em pouco tempo/i)).toBeInTheDocument();
  });
  expect(screen.getByRole('button', { name: /tentar novamente/i })).toBeInTheDocument();
});
MSW (Mock Service Worker) — mockando na camada de rede

jest.mock substitui o módulo JavaScript — funciona bem, mas exige mockar cada função separadamente. O MSW intercepta a requisição HTTP em si (na camada de rede), permitindo testar o código exatamente como ele chama fetch de verdade, sem mockar módulos internos. É mais realista e escala melhor para apps com muitas chamadas de API.

JavaScript — configurando MSW para interceptar a API de IA
// mocks/handlers.js
import { http, HttpResponse, delay } from 'msw';

export const handlers = [
  http.post('/api/chat', async ({ request }) => {
    const body = await request.json();
    const ultimaMensagem = body.mensagens.at(-1).content;

    await delay(50); // simula latência mínima, sem deixar o teste lento

    if (ultimaMensagem.includes('erro')) {
      return new HttpResponse(null, { status: 500 });
    }

    return HttpResponse.json({ content: `Resposta simulada para: "${ultimaMensagem}"` });
  }),
];

// mocks/server.js — servidor de mocks para os testes (Node)
import { setupServer } from 'msw/node';
import { handlers } from './handlers';
export const server = setupServer(...handlers);

// setupTests.js — liga o servidor antes de todos os testes
import { server } from './mocks/server';
beforeAll(() => server.listen());
afterEach(() => server.resetHandlers()); // limpa overrides entre testes
afterAll(() => server.close());

// Chatbot.test.jsx — usando o handler global e sobrescrevendo por teste
import { http, HttpResponse } from 'msw';
import { server } from './mocks/server';

test('trata erro 500 da API de IA com mensagem amigável', async () => {
  // Sobrescreve o handler SÓ para este teste
  server.use(
    http.post('/api/chat', () => new HttpResponse(null, { status: 500 }))
  );

  const user = userEvent.setup();
  render(<Chatbot />);
  await user.type(screen.getByRole('textbox'), 'oi{Enter}');

  await waitFor(() => {
    expect(screen.getByText(/algo deu errado/i)).toBeInTheDocument();
  });
});
jest.mock vs MSW — quando usar cada um: jest.mock é mais rápido de configurar para testes pontuais de um módulo isolado. MSW é preferível quando o app tem várias chamadas de API espalhadas, quando você quer testar o código de fetch em si (não só o componente que o chama), ou quando o mesmo mock de rede será reusado tanto em testes quanto durante desenvolvimento local (MSW funciona no browser também, não só em testes).
🙋 Qual a principal diferença entre mockar com jest.mock('./api/chamarIA') e usar MSW para mockar a mesma chamada?
A
Não há diferença nenhuma — são exatamente a mesma técnica com nomes diferentes
B
jest.mock substitui o módulo JS inteiro (a função chamarIA em si); MSW intercepta a requisição na camada de rede, então o código real de fetch continua sendo executado e testado
C
MSW só funciona com Axios, nunca com fetch nativo
D
jest.mock é mais lento porque precisa iniciar um servidor de verdade

LAB — Suíte de testes completa para o componente de chatbot
Objetivo: escrever uma suíte de testes para o chatbot cobrindo renderização inicial, envio de mensagem com resposta mockada, estado de erro com retry, e verificações básicas de acessibilidade — sem nenhuma chamada de rede real.
Passo a passo do LAB
1
Configurar o ambiente de testes
Instale jest, @testing-library/react, @testing-library/jest-dom, @testing-library/user-event e msw. Crie o arquivo setupTests.js importando '@testing-library/jest-dom' e configurando o servidor MSW (beforeAll/afterEach/afterAll).
2
Teste de renderização inicial
Verifique que o chatbot renderiza vazio: o campo de texto está presente (getByRole 'textbox'), o botão de enviar está desabilitado, e não há nenhuma mensagem na tela (queryByRole 'log' sem filhos, ou histórico vazio).
3
Teste de envio com resposta mockada (MSW)
Configure um handler MSW para /api/chat retornando uma resposta fixa. Digite uma mensagem com user-event, pressione Enter, e use waitFor para confirmar que a bubble do usuário E a resposta da IA aparecem na tela, nessa ordem.
4
Teste de estado de erro com retry
Sobrescreva o handler MSW para retornar status 429 nesse teste específico (server.use). Verifique que a mensagem de erro amigável aparece e que o botão "Tentar novamente" está presente e clicável.
5
Teste de acessibilidade básica
Verifique que o container do histórico tem role="log", que o textarea tem um nome acessível (getByRole 'textbox', { name: ... }), e que os botões de thumbs up/down têm aria-label. Isso serve como uma rede de segurança contra regressões de acessibilidade da Semana 14.
6
Rodar a suíte e checar cobertura
Rode npx jest --coverage. Analise o relatório: quais arquivos/linhas não foram exercitados por nenhum teste? Não busque 100% de cobertura — priorize os caminhos críticos (envio, erro, retry) sobre cobertura de vaidade.
React — suíte completa de Chatbot.test.jsx
import { render, screen, waitFor, within } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { http, HttpResponse } from 'msw';
import { server } from './mocks/server';
import { Chatbot } from './Chatbot';

describe('Chatbot', () => {

  test('renderiza vazio, com botão de enviar desabilitado', () => {
    render(<Chatbot />);
    expect(screen.getByRole('textbox', { name: /digite sua mensagem/i })).toBeInTheDocument();
    expect(screen.getByRole('button', { name: /enviar/i })).toBeDisabled();
    expect(screen.queryByRole('log')).toBeEmptyDOMElement();
  });

  test('envia mensagem e exibe a resposta mockada da IA', async () => {
    server.use(
      http.post('/api/chat', () => HttpResponse.json({ content: 'Resposta de teste.' }))
    );

    const user = userEvent.setup();
    render(<Chatbot />);

    await user.type(screen.getByRole('textbox'), 'Olá, IA{Enter}');

    const historico = screen.getByRole('log');
    expect(within(historico).getByText('Olá, IA')).toBeInTheDocument();

    await waitFor(() => {
      expect(within(historico).getByText('Resposta de teste.')).toBeInTheDocument();
    });
  });

  test('exibe erro amigável e botão de retry em falha de rede', async () => {
    server.use(
      http.post('/api/chat', () => new HttpResponse(null, { status: 429 }))
    );

    const user = userEvent.setup();
    render(<Chatbot />);
    await user.type(screen.getByRole('textbox'), 'oi{Enter}');

    await waitFor(() => {
      expect(screen.getByText(/muitas mensagens em pouco tempo/i)).toBeInTheDocument();
    });
    expect(screen.getByRole('button', { name: /tentar novamente/i })).toBeInTheDocument();
  });

  test('botões de feedback têm nome acessível', async () => {
    server.use(
      http.post('/api/chat', () => HttpResponse.json({ content: 'ok' }))
    );
    const user = userEvent.setup();
    render(<Chatbot />);
    await user.type(screen.getByRole('textbox'), 'oi{Enter}');

    await waitFor(() => {
      expect(screen.getByRole('button', { name: /resposta útil/i })).toBeInTheDocument();
      expect(screen.getByRole('button', { name: /resposta não útil/i })).toBeInTheDocument();
    });
  });
});

Exercício 01 — Teste unitário para traduzirErro()

Escreva testes unitários para a função traduzirErro() criada na Semana 12. Cubra pelo menos: status 429 (rate limit), status 401 (autenticação), status 400 com mensagem contendo "context length", erro de rede (offline) e o caso genérico de fallback. Use toEqual para verificar o objeto completo retornado.

Jest
JavaScript — traduzirErro.test.js
import { traduzirErro } from './traduzirErro';

describe('traduzirErro', () => {
  test('traduz rate limit (429)', () => {
    const resultado = traduzirErro({ status: 429 });
    expect(resultado.titulo).toBe('Muitas mensagens em pouco tempo');
    expect(resultado.acao).toBe('retry');
  });

  test('traduz erro de autenticação (401)', () => {
    const resultado = traduzirErro({ status: 401 });
    expect(resultado.acao).toBe('none');
    expect(resultado.titulo).toMatch(/autenticação/i);
  });

  test('traduz contexto muito longo (400)', () => {
    const resultado = traduzirErro({ status: 400, message: 'context length exceeded' });
    expect(resultado.acao).toBe('new-chat');
  });

  test('trata falha de rede (offline)', () => {
    const spy = jest.spyOn(navigator, 'onLine', 'get').mockReturnValue(false);
    const resultado = traduzirErro({ message: 'fetch failed' });
    expect(resultado.titulo).toMatch(/sem conexão/i);
    spy.mockRestore();
  });

  test('cai no fallback genérico para erros desconhecidos', () => {
    const resultado = traduzirErro({ status: 500 });
    expect(resultado.acao).toBe('retry');
    expect(resultado.titulo).toBe('Algo deu errado');
  });
});
Exercício 02 — Testando a store Zustand isoladamente

Escreva testes para a store useChatStore da Semana 16, sem renderizar nenhum componente React — acesse o hook diretamente via useChatStore.getState() nos testes. Verifique: novaConversa() cria uma conversa e a torna ativa, adicionarMensagem() adiciona à conversa correta, e excluirConversa() remove a conversa e limpa conversaAtivaId se ela era a ativa.

LAB
JavaScript — useChatStore.test.js
import { useChatStore } from './useChatStore';

// Reseta a store para um estado limpo antes de cada teste
beforeEach(() => {
  useChatStore.setState({ conversas: [], conversaAtivaId: null });
});

test('novaConversa cria e ativa uma conversa', () => {
  useChatStore.getState().novaConversa();
  const { conversas, conversaAtivaId } = useChatStore.getState();

  expect(conversas).toHaveLength(1);
  expect(conversaAtivaId).toBe(conversas[0].id);
});

test('adicionarMensagem adiciona à conversa ativa correta', () => {
  useChatStore.getState().novaConversa();
  useChatStore.getState().adicionarMensagem({ role: 'user', content: 'oi' });

  const { conversas, conversaAtivaId } = useChatStore.getState();
  const ativa = conversas.find(c => c.id === conversaAtivaId);
  expect(ativa.mensagens).toHaveLength(1);
  expect(ativa.mensagens[0].content).toBe('oi');
});

test('excluirConversa limpa conversaAtivaId se era a ativa', () => {
  useChatStore.getState().novaConversa();
  const id = useChatStore.getState().conversaAtivaId;

  useChatStore.getState().excluirConversa(id);
  const { conversas, conversaAtivaId } = useChatStore.getState();

  expect(conversas).toHaveLength(0);
  expect(conversaAtivaId).toBeNull();

Exercício 03 — Mockando streaming token a token

O chatbot da Semana 7 recebe a resposta via streaming (tokens chegando um a um), não como um JSON único. Configure um handler MSW usando ReadableStream para simular tokens chegando com pequenos delays, e escreva um teste que verifica que o texto na tela cresce progressivamente (verificar um estado intermediário parcial, depois o texto completo).

MSW · Streaming
JavaScript — handler MSW simulando streaming
import { http, HttpResponse, delay } from 'msw';

function criarStreamDeTokens(tokens, delayMs = 10) {
  const encoder = new TextEncoder();
  return new ReadableStream({
    async start(controller) {
      for (const token of tokens) {
        await new Promise(r => setTimeout(r, delayMs));
        controller.enqueue(encoder.encode(token));
      }
      controller.close();
    },
  });
}

// Handler que simula tokens chegando aos poucos
http.post('/api/chat/stream', () => {
  const tokens = ['Pa', 'ris', ' é', ' a', ' capital', ' da', ' França.'];
  return new HttpResponse(criarStreamDeTokens(tokens), {
    headers: { 'Content-Type': 'text/event-stream' },
  });
});

// Teste — verifica crescimento progressivo do texto
test('texto cresce progressivamente durante o streaming', async () => {
  const user = userEvent.setup();
  render(<Chatbot />);
  await user.type(screen.getByRole('textbox'), 'Qual a capital?{Enter}');

  // Estado intermediário — texto parcial já visível antes do fim do stream
  await waitFor(() => {
    expect(screen.getByText(/^Pa/)).toBeInTheDocument();
  });

  // Estado final — texto completo após o stream fechar
  await waitFor(() => {
    expect(screen.getByText('Paris é a capital da França.')).toBeInTheDocument();
  }, { timeout: 2000 });
});

Pirâmide de testes

Muitos unitários (Jest), camada média de integração (RTL), poucos E2E (Playwright). Foco principal em integração para apps de IA.

RTL e comportamento

getByRole antes de getByTestId. Testar o que o usuário vê e faz, não detalhes de implementação interna. user-event simula interação real.

Mocks de API de IA

Nunca chamar a API real nos testes. jest.mock substitui o módulo; MSW intercepta na camada de rede. Streaming pode ser simulado com ReadableStream.

Cobertura com critério

Priorizar caminhos críticos (envio, erro, retry, acessibilidade) sobre 100% de cobertura. waitFor para asserções assíncronas.
