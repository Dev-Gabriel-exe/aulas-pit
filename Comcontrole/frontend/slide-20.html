O critério WCAG 2.1 1.4.3 (Contraste Mínimo, nível AA) exige qual razão mínima de contraste para texto normal?
A
2:1
B
3:1
C
4.5:1
D
7:1
✅ Alternativa C. O critério 1.4.3 (nível AA) exige razão de contraste ≥ 4.5:1 para texto normal (abaixo de 18pt ou 14pt em negrito) e ≥ 3:1 apenas para texto grande. 7:1 é o exigido pelo critério 1.4.6 (nível AAA, mais rigoroso).

a11y
Um chatbot exibe novos tokens em uma <div> comum, sem nenhum atributo ARIA. Qual combinação resolve o problema de leitores de tela não anunciarem as novas mensagens?
A
tabindex="0" na div
B
role="log" + aria-live="polite"
C
aria-label em cada palavra
D
trocar a div por um <span>
✅ Alternativa B. aria-live="polite" instrui o leitor de tela a anunciar mudanças de conteúdo naquela região sem interromper agressivamente. role="log" complementa indicando que é uma região que recebe adições ao final — a combinação usada no histórico de mensagens de um chatbot.

a11y
Por que usar :focus-visible em vez de :focus para estilizar o indicador de foco?
A
São exatamente a mesma coisa, só nomes diferentes
B
:focus-visible funciona apenas em Safari
C
:focus-visible só exibe o indicador quando a navegação é por teclado, evitando o anel aparecer em cliques de mouse
D
:focus-visible desabilita completamente a navegação por mouse
✅ Alternativa C. :focus dispara tanto para clique quanto para teclado — o anel aparece mesmo ao clicar, o que muitos designers acham indesejado. :focus-visible é mais inteligente: só exibe o indicador quando o browser determina que a navegação é por teclado.

a11y
Qual é o propósito da classe utilitária "sr-only" (ou equivalente) usada em labels de botões de emoji?
A
Remove o elemento completamente da árvore de acessibilidade
B
Esconde visualmente o texto mas mantém acessível para leitores de tela
C
Aumenta o tamanho da fonte apenas para leitores de tela
D
Só funciona dentro de tabelas
✅ Alternativa B. A classe sr-only usa técnicas de CSS (position:absolute, clip, width/height de 1px) para ocultar visualmente um texto sem removê-lo da árvore de acessibilidade — ao contrário de display:none ou visibility:hidden, que removem o elemento completamente para leitores de tela também.
Bloco 2 — Performance (Semana 15)
5
perf
Quais são os limites de "bom" desempenho (nível verde) para LCP e INP segundo o Google?
A
LCP ≤ 1s, INP ≤ 50ms
B
LCP ≤ 2.5s, INP ≤ 200ms
C
LCP ≤ 5s, INP ≤ 500ms
D
LCP ≤ 10s, INP ≤ 1000ms
✅ Alternativa B. LCP (Largest Contentful Paint) "bom" é ≤ 2.5s. INP (Interaction to Next Paint) "bom" é ≤ 200ms. Esses são os limiares que o Google usa como referência de boa experiência do usuário nos Core Web Vitals.
6
perf
Um chatbot com Transformers.js roda a inferência do modelo na thread principal. Qual é a consequência mais provável para o INP?
A
Nenhuma — a inferência não afeta métricas de interação
B
O INP melhora, pois a thread principal fica mais ocupada e otimizada
C
O INP piora, pois a inferência bloqueia a atualização visual até terminar
D
O INP só é afetado se o modelo tiver mais de 1GB
✅ Alternativa C. Inferência rodando na thread principal bloqueia todo o JavaScript, incluindo a atualização da UI que mostraria feedback ao clique do usuário. A correção é mover a inferência para um Web Worker, liberando a thread principal.
7
perf
O que React.lazy() + Suspense permitem fazer em termos de bundle?
A
Compactar todo o CSS em um único arquivo
B
Carregar um componente (e seu código) somente quando ele for de fato renderizado, dividindo o bundle em chunks
C
Eliminar completamente a necessidade de testes
D
Rodar o React sem JavaScript no cliente
✅ Alternativa B. React.lazy() faz o import dinâmico de um componente, cujo código só é baixado quando ele é renderizado pela primeira vez. Suspense exibe um fallback enquanto esse chunk carrega — a base do code splitting em React.
8
perf
Por que importar seletivamente um tema do react-syntax-highlighter (em vez do pacote completo de temas) reduz o bundle em centenas de KB?
A
Porque o React remove automaticamente qualquer CSS não utilizado
B
Porque a importação completa inclui dezenas de temas não usados, e a seletiva evita empacotar esse código morto
C
Porque temas de highlight são sempre carregados via streaming
D
Não há diferença real de tamanho, apenas de organização
✅ Alternativa B. O pacote completo empacota todos os temas disponíveis mesmo que só um seja usado. Importar diretamente o caminho do tema específico evita ~840KB de código morto no bundle final — um dos ajustes de maior impacto visto na Semana 15.
Bloco 3 — Estado Global (Semana 16)
9
estado
Qual é o principal problema de usar Context API para armazenar estado que muda com alta frequência (ex: streaming de mensagens)?
A
Context API não suporta arrays
B
Todo componente que consome o Context re-renderiza a cada mudança do value, mesmo usando só uma fatia dele
C
Context API exige um servidor Redis para funcionar
D
Context API não pode ser usado dentro de componentes funcionais
✅ Alternativa B. Qualquer mudança no value de um Provider re-renderiza todos os consumidores daquele Context, independente de qual fatia específica cada um usa. Em estado de alta frequência (streaming), isso gera re-renders em cascata desnecessários.
10
estado
Como o Zustand evita o problema de re-render em cascata que a Context API tem?
A
Ele não permite múltiplos componentes lerem a mesma store
B
Ele força o uso de Redux por baixo dos panos
C
Seletores granulares (useStore(estado => estado.campo)) fazem o componente re-renderizar só quando aquela fatia específica muda
D
Ele desabilita o React Strict Mode automaticamente
✅ Alternativa C. O Zustand compara o retorno do seletor entre renders e só dispara re-render se aquele valor específico mudou — diferente da Context API, que propaga qualquer mudança do value para todos os consumidores.
11
estado
No middleware persist do Zustand, qual é a função do partialize?
A
Compactar o JSON salvo no localStorage usando gzip
B
Escolher quais campos da store são persistidos, permitindo excluir estado transitório como "streaming: true"
C
Dividir a store em múltiplos arquivos separados
D
Criptografar automaticamente os dados sensíveis
✅ Alternativa B. partialize decide o que sobrevive a um reload da página, permitindo excluir campos transitórios (como um "streaming: true" que não faz sentido persistir) e manter só o que deve de fato ser recuperado, como o histórico de conversas.
12
estado
Em qual cenário Redux Toolkit tende a compensar mais que Zustand?
A
Sempre — Redux Toolkit é superior em qualquer projeto
B
Em times grandes, projetos de longa duração com convenções rígidas, ou quando há necessidade de ferramentas como RTK Query e DevTools nativo
C
Apenas quando o projeto não faz nenhuma chamada de API
D
Zustand não pode persistir dados, então RTK é sempre obrigatório
✅ Alternativa B. Não existe uma escolha universalmente "melhor" — é um trade-off. Zustand é mais ágil para projetos pequenos/médios; RTK compensa em times grandes com mais convenções e ferramentas de ecossistema.
Bloco 4 — Testes de Front-end (Semana 17)
13
testes
Por que testes de front-end de um chatbot de IA nunca devem chamar a API real da OpenAI/HuggingFace durante a suíte?
A
Porque o Jest bloqueia tecnicamente qualquer chamada de rede
B
Porque a resposta é não-determinística, a chamada é lenta e custosa, e depende de rede/API key válida
C
Porque as APIs de IA bloqueiam automaticamente ferramentas de teste
D
Não há problema real, é apenas uma convenção estética
✅ Alternativa B. Não-determinismo, custo e dependência de rede/API key tornam a API real inviável para testes automatizados. A prática correta é mockar sempre a camada de IA com jest.mock ou MSW.
14
testes
Qual é a principal diferença entre jest.mock('./api/chamarIA') e usar MSW para mockar a mesma chamada?
A
Não há diferença nenhuma entre as duas técnicas
B
jest.mock substitui o módulo JS inteiro; MSW intercepta a requisição na camada de rede, mantendo o código real de fetch em execução
C
MSW só funciona com Axios, nunca com fetch nativo
D
jest.mock é mais lento pois inicia um servidor de verdade
✅ Alternativa B. jest.mock troca a função/módulo inteiro. MSW opera na camada de rede, deixando o código real de fetch/axios ser exercitado de fato — só a resposta do "servidor" é fake, tornando o teste mais fiel ao comportamento real.

testes
Por que a React Testing Library recomenda getByRole antes de getByTestId?
A
getByTestId é mais lento de executar durante a suíte
B
getByRole reflete o que tecnologia assistiva percebe; se falhar, geralmente revela um problema real de acessibilidade
C
data-testid não é suportado pelo Jest
D
Não há diferença real de propósito entre as duas queries
✅ Alternativa B. getByRole busca pela árvore de acessibilidade — a mesma forma como leitores de tela enxergam a página. Falhar nessa query geralmente expõe falta de aria-label ou semântica correta, não um problema do teste em si.

testes

A
Muitos E2E, poucos unitários
B
Quantidade igual de unitários, integração e E2E

Bloco 5 — Deploy e CI/CD (Semana 18)
17
deploy
Um estudante configura a chave da OpenAI na Vercel como VITE_OPENAI_KEY e a usa direto em um componente React. Isso é seguro em produção?
A
Sim, configurar no dashboard da Vercel já protege a chave automaticamente
B
Não — o prefixo VITE_ injeta a variável no bundle do cliente, expondo a chave via DevTools, independente de onde foi configurada
C
Sim, desde que o domínio use HTTPS
D
Depende apenas de a chave ter sido gerada recentemente
✅ Alternativa B. O prefixo VITE_ instrui o Vite a injetar a variável no bundle JavaScript enviado ao browser — uma decisão de design da ferramenta, não um bug. A única forma segura é usar uma variável sem esse prefixo, consumida apenas dentro de uma API Route.

deploy
O que é um Preview Deployment na Vercel?
A
A versão de produção que substitui automaticamente o app antigo
B
Uma URL única e isolada gerada para cada Pull Request/branch, sem afetar a produção
C
Um ambiente que só funciona localmente, nunca publicado
D
Um recurso exclusivo para projetos Next.js
✅ Alternativa B. A cada Pull Request ou push em uma branch diferente da main, a Vercel gera automaticamente uma URL de Preview isolada e totalmente funcional, sem impactar a versão de produção.

A
Não existe diferença real entre as duas abordagens
B
O rollback aponta o domínio de produção para um deploy anterior já buildado, sem rodar um novo ciclo de build, sendo muito mais rápido
