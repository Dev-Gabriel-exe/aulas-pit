Core Web Vitals, bundle analysis e o custo real de apps de IA
Core Web Vitals — as métricas que o Google mede

O Google criou o programa Core Web Vitals para padronizar como medimos a experiência do usuário. Desde 2021, elas são sinal de ranking. Para apps de IA, LCP e INP são os mais críticos — carregar o bundle de um modelo ou processar tokens pode facilmente exceder os thresholds.

LCP
Largest Contentful Paint
✅ Bom: ≤ 2.5s ⚠ Melhora: ≤ 4.0s ❌ Ruim: > 4.0s
Tempo até o maior elemento visível carregar. Em chatbots: a área de mensagens ou o título da página.
INP
Interaction to Next Paint
✅ Bom: ≤ 200ms ⚠ Melhora: ≤ 500ms ❌ Ruim: > 500ms
Latência de interação. Inferência de Transformers.js na thread principal bloqueia o INP — use Web Worker.
CLS
Cumulative Layout Shift
✅ Bom: ≤ 0.1 ⚠ Melhora: ≤ 0.25 ❌ Ruim: > 0.25
Layout se movendo enquanto o usuário lê. Em chatbots: skeletons sem altura definida causam shift ao carregar.
CLS em chatbots: quando o skeleton não tem a mesma altura que o conteúdo real, a página "pula" ao renderizar a resposta. Defina min-height nos bubbles de chat e evite deixar elementos sem dimensões explícitas antes de carregarem.
O peso real do bundle de um app de IA

Apps de IA acumulam dependências pesadas rapidamente. Um chatbot com markdown, highlight e gráficos pode ter um bundle inicial de 2–4MB — antes de qualquer código do desenvolvedor. Entender de onde vem o peso é o primeiro passo para otimizar.

Code splitting, lazy loading, useMemo e caching de modelos
Code splitting com React.lazy e Suspense

Por padrão, o Vite/CRA coloca todo o app em um único bundle JS. O usuário baixa todo o código antes de ver qualquer coisa — incluindo componentes que só serão usados depois (gráficos, markdown renderer, configurações). Code splitting divide o bundle em partes menores que são carregadas sob demanda.

React.lazy() faz o import dinâmico de um componente — o bundle desse componente só é baixado quando ele vai ser renderizado pela primeira vez. Suspense exibe um fallback enquanto o chunk está carregando.

React — lazy loading de componentes pesados
import { lazy, Suspense } from 'react';

// Componentes pesados são carregados apenas quando necessários
// O bundle do MarkdownRenderer (~180KB) só é baixado na primeira mensagem
const MarkdownRenderer = lazy(() => import('./MarkdownRenderer'));

// Recharts inteiro (~480KB) só carrega quando o dashboard é aberto
const Dashboard = lazy(() => import('./Dashboard'));

// O classificador de imagem (TF.js ~3MB) só carrega quando o usuário navega para essa rota
const ClassificadorImagem = lazy(() => import('./ClassificadorImagem'));

function App() {
  return (
    <BrowserRouter>
      <Routes>
        {/* Rota do chatbot — MarkdownRenderer carregado sob demanda */}
        <Route path="/" element={
          <Suspense fallback={<SkeletonBubble />}>
            <Chatbot />
          </Suspense>
        } />

        {/* Rota do dashboard — Recharts não entra no bundle inicial */}
        <Route path="/dashboard" element={
          <Suspense fallback={<div>Carregando dashboard...</div>}>
            <Dashboard />
          </Suspense>
        } />

        {/* Rota do classificador — TF.js fica fora do bundle principal */}
        <Route path="/classificar" element={
          <Suspense fallback={<CarregandoModelo />}>
            <ClassificadorImagem />
          </Suspense>
        } />
      </Routes>
    </BrowserRouter>
  );
}

useMemo e useCallback — quando memorizar compensa

useMemo e useCallback são ferramentas de otimização — não devem ser usados por padrão em todo lugar. Eles têm custo de memória e de comparação de dependências. São indicados especificamente quando um cálculo é caro (lento) e o componente re-renderiza frequentemente.

HookO que fazQuando usar em IAQuando NÃO usar
useMemoMemoriza o resultado de um cálculo entre rendersSimilaridade de cosseno entre embeddings (array.map + Math.sqrt por 384 dims). Filtro de histórico de conversas (slice, find em arrays grandes)Cálculos simples (somar 2 números). Props que mudam todo render mesmo assim
useCallbackMemoriza uma referência de função entre rendersFunção analisar() passada como prop para componente filho em Worker (evita recriar o Worker). Handlers de evento em listas longas de mensagensFunções que não são passadas como prop ou dependência de useEffect
React — useMemo para busca semântica cara
// Sem useMemo: cosSim é recalculado a cada render mesmo sem mudar
// Com 1000 embeddings × 384 dims = 384.000 operações por render
const resultadosBusca = useMemo(() => {
  if (!queryEmbedding || embeddingsProdutos.length === 0) return [];

  return embeddingsProdutos
    .map((emb, i) => ({
      produto: produtos[i],
      score: cosSim(queryEmbedding, emb)  // 384 operações por produto
    }))
    .sort((a, b) => b.score - a.score)
    .slice(0, 5);

// Dependências: só recalcula quando query ou produtos mudam
}, [queryEmbedding, embeddingsProdutos]);

// useCallback para a função de análise passada ao componente filho
const analisarTexto = useCallback((texto) => {
  return new Promise((resolve, reject) => {
    const id = ++contadorId.current;
    pendentesRef.current[id] = { resolve, reject };
    workerRef.current?.postMessage({ tipo: 'analisar', texto, id });
  });
}, []); // [] = referência estável — não recria a função entre renders
Caching de modelos de IA — nunca baixar duas vezes

O MobileNet (~16MB) e o DistilBERT (~17MB) fazem um download significativo na primeira visita. Sem caching, cada vez que o usuário retorna ao site ele precisa baixar tudo de novo. Com uma estratégia de cache correta, o modelo fica persistido e carrega instantaneamente.

EstratégiaComo funcionaMelhor paraLimitação
HTTP Cache (automático)Browser armazena arquivos com base nos headers Cache-Control do servidorAssets estáticos com URL imutável (ex: modelo.v2.bin)Não funciona offline. Expiração depende do servidor
IndexedDB (TF.js nativo)tf.loadLayersModel('indexeddb://model') persiste o modelo localmenteModelos Keras customizados carregados via TF.jsTamanho limitado por quota do browser (~50MB–1GB)
Cache API (Service Worker)Intercepta requests dos pesos do modelo e serve do cache localTransformers.js — pesos ficam no Cache Storage offlineRequer Service Worker e HTTPS
Browser Cache automáticoTransformers.js usa o cache do browser por padrão via fetchPrimeira linha de cache — zero configuraçãoLimpo quando o usuário limpa dados do browser
JavaScript — persistindo modelo TF.js no IndexedDB
import * as tf from '@tensorflow/tfjs';
import * as mobilenet from '@tensorflow-models/mobilenet';

const CACHE_KEY = 'indexeddb://mobilenet-v2';

async function carregarComCache() {
  try {
    // Tenta carregar do IndexedDB (instantâneo se existir)
    const modelo = await tf.loadLayersModel(CACHE_KEY);
    console.log('✅ Modelo carregado do cache local');
    return modelo;
  } catch {
    // Primeira vez: baixa do servidor e salva no IndexedDB
    console.log('⬇ Baixando modelo pela primeira vez...');
    const modelo = await mobilenet.load({ version: 2, alpha: 1.0 });

    // Salva para uso futuro offline
    await modelo.model.save(CACHE_KEY);
    console.log('💾 Modelo salvo no IndexedDB para próximas visitas');
    return modelo;
  }
}

// O Transformers.js tem cache automático via browser fetch cache
// env.cacheDir configura onde os modelos ficam armazenados:
import { env } from '@xenova/transformers';
env.useBrowserCache = true;  // padrão — usa o cache HTTP do browser
// Na segunda visita, os pesos são servidos do cache sem nenhum download

Exercício 01 — Preloading do modelo em background

Em vez de carregar o MobileNet ou DistilBERT apenas quando o usuário abre o componente, inicie o download em background assim que o app carrega — enquanto o usuário ainda está lendo a página inicial. Use o hook useEffect no componente raiz App.jsx para chamar mobilenet.load() e guardar a Promise em um ref global. O componente filho que precisa do modelo await essa Promise em vez de iniciar um novo download.

LAB
React — preloading do modelo com ref global
// modelPromise.js — singleton compartilhado
import * as mobilenet from '@tensorflow-models/mobilenet';

let _modelPromise = null;

export function preloadModel() {
  // Inicia o download apenas uma vez — chamadas seguintes recebem a mesma Promise
  if (!_modelPromise) {
    _modelPromise = mobilenet.load({ version: 2, alpha: 1.0 });
  }
  return _modelPromise;
}

export function getModel() {
  return _modelPromise || preloadModel();
}

// No App.jsx — preload em background ao iniciar
useEffect(() => {
  preloadModel();  // fire-and-forget — não aguarda
}, []);

// No ClassificadorImagem.jsx — modelo já está carregando/carregado
useEffect(() => {
  async function init() {
    const m = await getModel();  // resolve imediatamente se já baixou
    setModelo(m);
    setCarregando(false);
  }
  init();
}, []);
Exercício 02 — Virtualização de lista de mensagens

Em conversas longas (100+ mensagens), renderizar todo o histórico no DOM é lento — o browser precisa calcular o layout de centenas de elementos. Implemente virtualização usando a biblioteca react-window: renderize apenas as mensagens visíveis na viewport + um buffer de 5 acima e abaixo. Compare o tempo de renderização e o número de nós DOM com e sem virtualização em uma conversa simulada de 200 mensagens.

LAB
React — lista virtualizada com react-window
import { VariableSizeList } from 'react-window';
import { useRef, useCallback } from 'react';

// Cache de alturas — mensagens longas têm alturas diferentes
const alturaCache = new Map();

function ListaMensagens({ historico }) {
  const listaRef = useRef(null);

  const getAltura = useCallback((index) => {
    return alturaCache.get(index) || 80;  // estimativa inicial
  }, []);

  const Linha = ({ index, style }) => {
    const m = historico[index];
    return (
      <div style={style}>
        <BubbleMensagem
          mensagem={m}
          onAlturaMedida={(h) => {
            if (alturaCache.get(index) !== h) {
              alturaCache.set(index, h);
              listaRef.current?.resetAfterIndex(index);
            }
          }}
        />
      </div>
    );
  };

  return (
    <VariableSizeList
      ref={listaRef}
      height={500}
      itemCount={historico.length}
      itemSize={getAltura}
      overscanCount={5}   // renderiza 5 itens fora da viewport
    >
      {Linha}
    </VariableSizeList>
  );
}
Exercício 03 — Otimização de imagens no classificador

No classificador de imagem da Semana 10, o usuário pode fazer upload de fotos grandes (3–10MB). Antes de enviar ao MobileNet: (1) redimensione a imagem para máximo 800×800px usando um canvas, (2) converta para WebP (20–30% menor que JPEG), (3) meça o tempo de inferência com a imagem original vs redimensionada. O MobileNet internamente redimensiona para 224×224 de qualquer forma — enviar uma imagem menor reduz o tempo de pré-processamento.

LAB
JavaScript — redimensionar imagem com Canvas antes da inferência
async function redimensionarImagem(arquivo, maxSize = 800) {
  const bitmap = await createImageBitmap(arquivo);
  const escala = Math.min(maxSize / bitmap.width, maxSize / bitmap.height, 1);

  const canvas = document.createElement('canvas');
  canvas.width  = Math.round(bitmap.width  * escala);
  canvas.height = Math.round(bitmap.height * escala);

  const ctx = canvas.getContext('2d');
  ctx.drawImage(bitmap, 0, 0, canvas.width, canvas.height);

  // Converte para WebP com qualidade 85% (menor que JPEG, mesma qualidade visual)
  return new Promise(resolve => {
    canvas.toBlob(resolve, 'image/webp', 0.85);
  });
}

// Uso na função de classificação:
async function aoSelecionarArquivo(arquivo) {
  const t0 = performance.now();
  const imagemOtimizada = await redimensionarImagem(arquivo);
  console.log(`Redimensionamento: ${(performance.now()-t0).toFixed(0)}ms`);
  console.log(`Original: ${(arquivo.size/1024).toFixed(0)}KB | Otimizada: ${(imagemOtimizada.size/1024).toFixed(0)}KB`);
  // Continua com a imagem otimizada para o MobileNet...
}
Exercício 04 — Desafio: Service Worker para cache offline

Implemente um Service Worker que intercep­ta os downloads dos pesos do modelo Transformers.js e os armazena na Cache API. Na segunda visita — mesmo offline — os pesos são servidos do cache local. Use a estratégia "Cache First": verifica o cache antes de ir para a rede. Implemente também um evento "install" que faz o pre-cache do bundle principal do app e um fallback para quando o usuário está completamente offline.

Desafio · Service Worker
JavaScript — sw.js (Service Worker com Cache First)
const CACHE_NAME = 'ai-app-v1';
const MODELO_CACHE = 'ai-models-v1';

// URLs de pesos do modelo para pré-cachear
const MODELO_URLS = [
  'https://cdn.jsdelivr.net/npm/@xenova/transformers@...',
];

self.addEventListener('install', event => {
  event.waitUntil(
    caches.open(CACHE_NAME).then(cache => cache.addAll([
      '/', '/index.html', '/offline.html'
    ]))
  );
});

// Cache First — para assets estáticos e pesos de modelo
self.addEventListener('fetch', event => {
  const url = new URL(event.request.url);

  // Pesos de modelo: sempre Cache First
  if (url.pathname.includes('.bin') || url.pathname.includes('.onnx')) {
    event.respondWith(
      caches.match(event.request).then(cached => {
        if (cached) return cached;  // servir do cache

        // Não está no cache — baixar e salvar para próximas vezes
        return fetch(event.request).then(response => {
          const copia = response.clone();
          caches.open(MODELO_CACHE).then(cache => cache.put(event.request, copia));
          return response;
        });
      })
    );
  }
});
