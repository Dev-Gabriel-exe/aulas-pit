Transformers.js — da API Python ao browser com ONNX
O que é Transformers.js e como funciona

O Transformers.js é a port JavaScript da biblioteca HuggingFace Transformers. Ele usa o ONNX Runtime Web como engine de execução — os modelos são convertidos do formato PyTorch para ONNX (Open Neural Network Exchange) e quantizados para reduzir o tamanho, mantendo boa parte da acurácia.

A grande vantagem: a mesma API que você usa em Python agora funciona no browser. pipeline("sentiment-analysis") em Python e em JavaScript funcionam identicamente — mesmo conceito de pipeline, mesmo modelo do HuggingFace Hub, mesmo formato de saída.

Python (HuggingFace)
from transformers import pipeline

classificador = pipeline("sentiment-analysis")
resultado = classificador("I love this!")
# [{'label': 'POSITIVE', 'score': 0.9998}]
JavaScript (Transformers.js)
import { pipeline } from '@xenova/transformers';

const classificador = await pipeline("sentiment-analysis");
const resultado = await classificador("I love this!");
// [{label: 'POSITIVE', score: 0.9998}]
Como os modelos chegam ao browser: o Transformers.js baixa automaticamente os pesos ONNX quantizados do HuggingFace Hub na primeira execução e os armazena no cache do browser (IndexedDB). Chamadas seguintes são instantâneas — sem download. Modelos como distilbert-base-uncased-finetuned-sst-2-english chegam a ~67MB; versões INT8 quantizadas ficam em ~17MB.

Limitação real: modelos como GPT-2 (90MB INT8) e BART-large (400MB) são pesados para o browser. O download inicial pode levar 30–60 segundos em conexões lentas. Para geração de texto de qualidade, ainda vale a pena usar a API da OpenAI (Semana 5). Transformers.js brilha em tarefas focadas: sentimento, embedding, NER e tradução com modelos leves.
🙋 Por que o Transformers.js usa o formato ONNX em vez de carregar diretamente pesos PyTorch (.pt)?
A
ONNX é mais fácil de debugar — os pesos ficam em texto legível no browser
B
PyTorch não roda no browser — ONNX é um formato neutro executável pelo ONNX Runtime Web via WebAssembly/WebGL, sem precisar do Python runtime
C
ONNX comprime os pesos melhor do que PyTorch — modelos ficam 10x menores automaticamente
D
É apenas uma preferência da HuggingFace — tecnicamente os dois formatos funcionam igual no browser

Embeddings — texto como coordenada no espaço semântico

Um embedding é uma representação vetorial de texto — uma lista de números (ex: 384 números no all-MiniLM-L6-v2) onde textos semanticamente similares ficam próximos no espaço vetorial. "Cachorro" e "cão" produzem vetores próximos; "cachorro" e "avião" produzem vetores distantes.

A similaridade de cosseno mede o ângulo entre dois vetores — 1.0 = idênticos, 0.0 = perpendiculares (sem relação), -1.0 = opostos. É a métrica padrão para busca semântica e deduplicação.

JavaScript — embeddings e similaridade de cosseno
import { pipeline } from '@xenova/transformers';

// Função de similaridade de cosseno entre dois vetores
function cosSim(a, b) {
  let dot = 0, normA = 0, normB = 0;
  for (let i = 0; i < a.length; i++) {
    dot   += a[i] * b[i];
    normA += a[i] * a[i];
    normB += b[i] * b[i];
  }
  return dot / (Math.sqrt(normA) * Math.sqrt(normB));
}

// Gerar embeddings e calcular similaridade
async function demo() {
  const extrator = await pipeline(
    'feature-extraction',
    'Xenova/all-MiniLM-L6-v2'   // modelo leve, 384 dims
  );

  const frases = [
    'O cachorro brinca no jardim',
    'O cão se diverte no quintal',
    'O avião aterrissou no aeroporto',
  ];

  // Gerar os três embeddings em paralelo
  const resultados = await Promise.all(
    frases.map(f => extrator(f, {
      pooling: 'mean',   // média dos tokens → vetor único
      normalize: true, // normaliza para norma unitária
    }))
  );

  // Extrair o vetor Float32Array de cada resultado
  const [v1, v2, v3] = resultados.map(r => Array.from(r.data));

  console.log('cachorro ↔ cão:    ', cosSim(v1, v2).toFixed(3)); // ~0.92
  console.log('cachorro ↔ avião:  ', cosSim(v1, v3).toFixed(3)); // ~0.08
}
Web Workers — inferência sem travar a UI

Transformers de NLP bloqueiam a thread principal por 100–500ms durante a inferência. Isso congela a interface — o usuário não consegue digitar, clicar ou rolar. A solução é mover toda a inferência para um Web Worker: uma thread JavaScript separada que roda em paralelo sem bloquear o DOM.

Arquitetura com Web Worker
Thread Principal (UI)
──postMessage(texto)──▶
Web Worker
— inferência roda aqui, sem bloquear UI
Thread Principal (UI)
◀─onmessage(resultado)─
Web Worker
— resultado enviado de volta após concluir
O modelo é carregado UMA VEZ no Worker e fica na memória. Cada análise é uma troca de mensagens. A UI permanece responsiva durante toda a inferência.
JavaScript — sentimento.worker.js
import { pipeline, env } from '@xenova/transformers';

// Desabilita cache local (opcional — útil em dev para sempre baixar fresco)
// env.useBrowserCache = false;

let classificador = null;

// Recebe mensagens da thread principal
self.addEventListener('message', async (evento) => {
  const { tipo, texto, id } = evento.data;

  if (tipo === 'carregar') {
    // Carrega o modelo uma única vez
    self.postMessage({ tipo: 'status', texto: 'Baixando modelo...' });
    classificador = await pipeline(
      'sentiment-analysis',
      'Xenova/distilbert-base-uncased-finetuned-sst-2-english',
      { progress_callback: (info) => {
          if (info.status === 'progress')
            self.postMessage({ tipo: 'progresso', pct: info.progress });
        }
      }
    );
    self.postMessage({ tipo: 'pronto' });
  }

  if (tipo === 'analisar' && classificador) {
    const resultado = await classificador(texto, { topk: null }); // todas as classes
    self.postMessage({ tipo: 'resultado', id, resultado });
  }
});
React — useAnaliseSentimento.js (hook para usar o worker)
import { useState, useEffect, useRef, useCallback } from 'react';

export function useAnaliseSentimento() {
  const [status, setStatus] = useState('inativo'); // inativo|carregando|pronto
  const [progresso, setProgresso] = useState(0);
  const workerRef = useRef(null);
  const pendentesRef = useRef({}); // map de id → {resolve, reject}
  let contadorId = useRef(0);

  useEffect(() => {
    // Cria o worker (Vite usa import.meta.url; CRA usa new URL)
    const worker = new Worker(
      new URL('./sentimento.worker.js', import.meta.url),
      { type: 'module' }
    );

    worker.addEventListener('message', ({ data }) => {
      if (data.tipo === 'status')    setStatus('carregando');
      if (data.tipo === 'progresso') setProgresso(data.pct);
      if (data.tipo === 'pronto')    { setStatus('pronto'); setProgresso(100); }
      if (data.tipo === 'resultado') {
        const pendente = pendentesRef.current[data.id];
        if (pendente) { pendente.resolve(data.resultado); delete pendentesRef.current[data.id]; }
      }
    });

    workerRef.current = worker;
    worker.postMessage({ tipo: 'carregar' });

    return () => worker.terminate();
  }, []);

  const analisar = useCallback((texto) => {
    return new Promise((resolve, reject) => {
      const id = ++contadorId.current;
      pendentesRef.current[id] = { resolve, reject };
      workerRef.current?.postMessage({ tipo: 'analisar', texto, id });
    });
  }, []);

  return { status, progresso, analisar };
}
Por que usar um Map de Promises (pendentesRef)? O Worker processa mensagens em sequência mas o usuário pode digitar rápido, gerando várias análises quase simultâneas. O mapa de id → {resolve} garante que cada resposta chegue à Promise certa, mesmo se chegarem fora de ordem. Sem isso, a última Promise resolveria todas as anteriores com o mesmo resultado.
🙋 Por que a inferência com Transformers.js deve sempre rodar em um Web Worker em vez da thread principal?
A
Web Workers têm acesso a mais memória RAM — necessário para modelos grandes
B
Inferência bloqueia a thread principal por 100–500ms, congelando a interface — o Worker roda em paralelo e permite que a UI permaneça responsiva durante toda a inferência
C
Workers têm acesso ao WebGPU — necessário para acelerar modelos de linguagem
D
É uma exigência do Transformers.js — a biblioteca só funciona dentro de Workers

React — AnalisadorSentimento.jsx completo
import { useState, useEffect, useRef } from 'react';
import { useAnaliseSentimento } from './useAnaliseSentimento';
import './AnalisadorSentimento.css';

const EXEMPLOS = [
  "Este produto é absolutamente incrível, superou todas as minhas expectativas!",
  "Péssimo serviço, nunca mais compro nada aqui. Total decepção.",
  "O produto chegou no prazo, nada de especial.",
];

export default function AnalisadorSentimento() {
  const { status, progresso, analisar } = useAnaliseSentimento();
  const [texto, setTexto] = useState('');
  const [resultado, setResultado] = useState(null);
  const [analisando, setAnalisando] = useState(false);
  const [tempoInferencia, setTempoInferencia] = useState(null);
  const debounceRef = useRef(null);

  useEffect(() => {
    if (!texto.trim() || status !== 'pronto') return;

    // Debounce: espera 400ms após o usuário parar de digitar
    clearTimeout(debounceRef.current);
    debounceRef.current = setTimeout(async () => {
      setAnalisando(true);
      const inicio = performance.now();
      try {
        const res = await analisar(texto);
        setResultado(res);
        setTempoInferencia((performance.now() - inicio).toFixed(0));
      } finally {
        setAnalisando(false);
      }
    }, 400);

    return () => clearTimeout(debounceRef.current);
  }, [texto, status, analisar]);

  // Encontrar o rótulo com maior score para destacar
  const labelDominante = resultado?.reduce((a, b) => a.score > b.score ? a : b);

  return (
    <div className="analisador">
      <h1>Análise de Sentimento</h1>
      <p className="sub">DistilBERT · 100% no browser · Privado por design</p>

      {/* Status de carregamento */}
      {status !== 'pronto' && (
        <div className="carregamento">
          <p>{status === 'inativo' ? 'Inicializando worker...' : `Baixando modelo... ${progresso.toFixed(0)}%`}</p>
          <div className="progresso-track">
            <div className="progresso-fill" style={{ width: `${progresso}%` }} />
          </div>
        </div>
      )}

      {/* Exemplos rápidos */}
      <div className="exemplos">
        {EXEMPLOS.map((ex, i) => (
          <button key={i} className="btn-exemplo"
            onClick={() => setTexto(ex)} disabled={status !== 'pronto'}>
            Exemplo {i + 1}
          </button>
        ))}
      </div>

      <textarea
        value={texto}
        onChange={e => setTexto(e.target.value)}
        placeholder="Digite seu texto aqui — a análise acontece automaticamente..."
        disabled={status !== 'pronto'}
        rows={4}
      />

      {analisando && <p className="status-analisando">⏳ Analisando...</p>}

      {resultado && !analisando && (
        <div className="resultado">
          <div className=`sentimento-tag ${labelDominante.label.toLowerCase()}`>
            {labelDominante.label === 'POSITIVE' ? '😊 Positivo' : '😞 Negativo'}
          </div>

          {resultado.map(item => (
            <div key={item.label} className="bar-row">
              <span className="bar-label">{item.label}</span>
              <div className="bar-track">
                <div
                  className={`bar-fill ${item.label.toLowerCase()}`}
                  style={{ width: `${(item.score * 100).toFixed(1)}%` }}
                />
              </div>
              <span className="bar-pct">{(item.score * 100).toFixed(1)}%</span>
            </div>
          ))}

          {tempoInferencia && (
            <p className="tempo">Inferência: {tempoInferencia}ms · Worker ativo</p>
          )}
        </div>
      )}
    </div>
  );
}

Exercício 02 — Busca semântica em lista de produtos

Use o pipeline feature-extraction com Xenova/all-MiniLM-L6-v2 para construir uma busca semântica. Dada uma lista de 10 produtos com descrições, pré-compute os embeddings de todos ao carregar a página. Quando o usuário digitar uma busca, compute o embedding da query e calcule a similaridade de cosseno com cada produto. Exiba os 3 mais similares — mesmo sem conter as mesmas palavras da query.

LAB · conceito
Estrutura — BuscaSemantica.jsx
// Ao carregar: pré-computar embeddings de todos os produtos
useEffect(() => {
  async function preComputar() {
    const extrator = await pipeline('feature-extraction', 'Xenova/all-MiniLM-L6-v2');
    const embs = await Promise.all(
      produtos.map(p => extrator(p.descricao, { pooling: 'mean', normalize: true }))
    );
    setEmbeddingsProdutos(embs.map(e => Array.from(e.data)));
    setExtrator(extrator);
  }
  preComputar();
}, []);

// Ao buscar:
async function buscar(query) {
  const embQuery = Array.from(
    (await extrator(query, { pooling: 'mean', normalize: true })).data
  );
  const scores = embeddingsProdutos
    .map((emb, i) => ({ produto: produtos[i], score: cosSim(embQuery, emb) }))
    .sort((a, b) => b.score - a.score)
    .slice(0, 3);
  setResultados(scores);
}
Exercício 03 — Análise de sentimento em múltiplos idiomas

O modelo DistilBERT-SST2 foi treinado em inglês. Teste a análise com textos em português e observe os resultados. Em seguida, substitua pelo modelo multilingual Xenova/bert-base-multilingual-uncased-sentiment (que classifica de 1 a 5 estrelas) e compare os resultados. Quais são as diferenças em tamanho do modelo, latência e qualidade das predições em PT-BR?

Experimentação
  • DistilBERT-SST2 em português: funciona parcialmente — o modelo nunca viu português, mas o tokenizador WordPiece decompõe palavras em subwords que podem ter algum sinal. Textos fortemente positivos/negativos geralmente acertam; textos neutros ou com gírias brasileiras falham com frequência.
  • bert-base-multilingual-sentiment: ~450MB no formato completo, ~110MB INT8. Saída são 5 classes (1-5 estrelas) em vez de POSITIVE/NEGATIVE. Muito melhor para PT-BR. Mas é 6x maior que o DistilBERT-SST2 — primeiro carregamento demora mais.
  • Lição prática: a escolha do modelo impacta tamanho, latência e qualidade em cada idioma. Para produção em PT-BR, um modelo fine-tuned em português (ex: neuralmind/bert-base-portuguese-cased) seria ideal — mas ainda não há uma versão Xenova/ONNX publicada para ele.
Exercício 04 — Desafio: geração de texto token a token

Use o pipeline text-generation com Xenova/gpt2 e o callback callback_function para implementar efeito de streaming — cada token gerado aparece imediatamente na tela, assim como na Semana 7. No Worker, passe { callback_function: (beams) => self.postMessage({tipo:'token', token: beams[0].output_token_ids}) } e reconstitua o texto acumulado no componente React.

Desafio
JavaScript — geração com streaming no Worker
// No geracao.worker.js:
let gerador = null;
let tokenizer = null;

self.addEventListener('message', async ({ data }) => {
  if (data.tipo === 'carregar') {
    const { pipeline, AutoTokenizer } = await import('@xenova/transformers');
    gerador   = await pipeline('text-generation', 'Xenova/gpt2');
    tokenizer = await AutoTokenizer.from_pretrained('Xenova/gpt2');
    self.postMessage({ tipo: 'pronto' });
  }

  if (data.tipo === 'gerar') {
    let textoAcumulado = '';
    await gerador(data.prompt, {
      max_new_tokens: 100,
      callback_function: (beams) => {
        const tokens = beams[0].output_token_ids;
        // decodifica apenas o último token novo
        const novoToken = tokenizer.decode([tokens[tokens.length - 1]], { skip_special_tokens: true });
        textoAcumulado += novoToken;
        self.postMessage({ tipo: 'token', token: novoToken, texto: textoAcumulado });
      }
    });
    self.postMessage({ tipo: 'fim' });
  }
});
