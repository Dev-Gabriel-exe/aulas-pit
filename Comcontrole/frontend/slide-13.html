Os 6 temas — pontos-chave e armadilhas comuns
Semana 7 — Streaming
EventSource: só GET, sem headers → não funciona direto com OpenAI (precisa Authorization)
fetch + ReadableStream: POST com headers livres, chunks via reader.read() + TextDecoder
Formato SSE: linhas data: JSON → filtrar, parsear, ignorar [DONE]
AbortController: cancelar stream → useRef (não useState) → e.name === 'AbortError'
Cursor piscante: span com animation blink → some quando gerando === false
textoCompleto: variável local acumuladora → setState ao fim para o histórico
Armadilha: guardar AbortController em useState causa re-render toda vez que é criado. Use useRef — persiste sem disparar renders.
Semana 8 — Markdown
dangerouslySetInnerHTML + IA: risco XSS real — scripts no conteúdo do modelo são executados
react-markdown: converte para componentes React, não HTML cru — sem XSS
remark-gfm: habilita tabelas, checklists, strikethrough (GFM não é markdown padrão)
components prop: sobrescreve como cada elemento é renderizado → BlocoCode para code
className="language-X": o react-markdown passa o prefixo "language-" na className do code
Streaming + markdown: texto puro durante geração → ReactMarkdown só após [DONE]
Armadilha: usar dangerouslySetInnerHTML com marked() em vez de react-markdown. Mesmo que "funcione", é vulnerabilidade XSS com conteúdo de LLM.
Semana 9 — Recharts
ResponsiveContainer: sempre o mais externo — ajusta width ao pai
dataKey: aponta para o campo do objeto de dados que a série vai plotar (campo numérico)
XAxis dataKey: o campo usado como categoria no eixo X (ex: "epoca", "classe")
LineChart: evolução temporal — accuracy/loss por época, overfitting visível
BarChart: comparação entre categorias — precision/recall por classe
PieChart: proporção — innerRadius > 0 = donut. Evitar com mais de 5 fatias
Tooltip customizado: componente React com active, payload, label
Armadilha: confundir dataKey do XAxis (campo categoria) com dataKey do Line/Bar (campo de valor). São props do mesmo nome mas em componentes diferentes e com significados opostos.
Semana 10 — TensorFlow.js
Tensor: array multidimensional na GPU (WebGL) — fora do GC do JavaScript
dispose(): libera memória GPU manualmente — obrigatório para evitar memory leak
tf.tidy(): descarta todos os tensores intermediários criados dentro do callback, retorna o final
tf.memory().numTensors: monitora leaks — não deve crescer a cada inferência
Pipeline MobileNet: Arquivo → DataURL → HTMLImage → fromPixels → resize → /127.5 − 1 → expandDims
model.classify(img, k): retorna [{className, probability}] — pré-processamento embutido no pacote
Armadilha: normalização deve ser IDÊNTICA ao treino. Se treinou com ÷255, inferir com ÷127.5−1 produz predições aleatórias.
Semana 11 — Transformers.js
ONNX Runtime Web: PyTorch não roda no browser → ONNX é formato neutro executado via WebAssembly/WebGL
pipeline("tarefa", "Xenova/modelo"): mesma API do Python — carrega modelo do HuggingFace Hub
Cache automático: pesos ficam no browser (IndexedDB) — download só na primeira vez
Web Worker obrigatório: inferência bloqueia a thread principal 100–500ms → UI congela sem worker
postMessage / onmessage: comunicação assíncrona entre thread principal e worker
Embeddings: feature-extraction + pooling:"mean" + normalize:true → vetor [384]
Similaridade cosseno: dot(a,b) / (|a| × |b|) → 1.0 = idêntico, 0.0 = sem relação
Armadilha: rodar pipeline() na thread principal. Em UI interativa, o usuário não consegue digitar durante a inferência. Worker é obrigatório — não opcional.
Semana 12 — UX para IA
useReducer: impede estados impossíveis (loading + error ao mesmo tempo) — todas as transições em um lugar
4 estados: idle → loading → success | error → loading (retry)
Skeleton: CSS shimmer animation — melhor que spinner porque informa shape do conteúdo
traduzirErro(): status HTTP → mensagem amigável + ação. Nunca expor stack trace
Disclaimer automático: detectar keywords críticas (médico, lei, investir) → nota no rodapé
Thumbs up/down: localStorage para persistir feedback — em prod: endpoint de analytics
Error Boundary: captura erros de renderização — try/catch NÃO captura erros no render do React
Armadilha: expor e.message bruto ao usuário (ex: "TypeError: Cannot read properties of undefined"). Use traduzirErro() para converter em linguagem humana.

Durante um stream, um chunk retorna a string "data: {\"choices\":[{\"delta\":{\"conten" — uma linha SSE cortada no meio. O que deve acontecer?
A
O stream deve ser cancelado — dados corrompidos invalidam toda a resposta
B
O JSON incompleto falha no JSON.parse — o try/catch silencia o erro e o próximo chunk trará o restante da linha
C
O TextDecoder remonta automaticamente as linhas cortadas entre chunks
D
Isso nunca acontece — o servidor sempre envia chunks alinhados às linhas SSE
✅ Alternativa B. Chunks chegam com tamanhos variáveis determinados pela rede e buffers do servidor — uma linha SSE pode chegar em múltiplos chunks. O try/catch dentro do loop é exatamente para capturar silenciosamente o SyntaxError do JSON.parse incompleto e aguardar o próximo chunk. Para máxima robustez, a solução avançada é acumular fragmentos em um buffer antes de tentar o parse.

Um LLM retorna uma resposta que contém <script>document.cookie</script>. Se você usar dangerouslySetInnerHTML com marked(), o que acontece?
A
Nada — o React sanitiza automaticamente o HTML antes de injetar no DOM
B
O script é renderizado como texto — browsers modernos bloqueiam scripts injetados via innerHTML
C
O script é executado no browser do usuário — isso é XSS real, podendo vazar cookies e dados
D
O marked() já sanitiza scripts — dangerouslySetInnerHTML é seguro quando combinado com marked
✅ Alternativa C. dangerouslySetInnerHTML injeta HTML diretamente no DOM sem qualquer sanitização do React. Sem. 10
Por que tensores no TensorFlow.js precisam de .dispose() ou tf.tidy() enquanto objetos JavaScript normais são coletados pelo GC automaticamente?
A
É uma convenção de API — tecnicamente o GC já cuida, .dispose() é apenas explicitação
B
Tensores vivem na memória da GPU (WebGL buffers) — fora do heap JavaScript e invisíveis ao GC do browser
C
Tensores são imutáveis — .dispose() libera o lock de leitura e permite reuso do buffer
D
É para segurança — .dispose() apaga os dados do tensor para impedir acesso não autorizado
✅ Alternativa B. O garbage collector do JavaScript gerencia o heap JS — onde vivem objetos, arrays, closures. Tensores do TF.js são alocados em buffers WebGL na memória da GPU, completamente fora do controle do GC. Sem dispose() ou tf.tidy(), esses buffers acumulam na VRAM até o browser travar. tf.memory().numTensors mostra o total ativo — deve ser estável a cada inferência.

Sem. 10
O MobileNet foi treinado com imagens normalizadas para [-1, 1] usando pixel/127.5 - 1. Se você fizer inferência com pixels normalizados para [0, 1] usando apenas pixel/255, o que acontece com as predições?
A
As predições são levemente menos precisas — a diferença é pequena e aceitável
B
O modelo detecta a normalização errada e a corrige internamente antes da inferência
C
As predições são essencialmente aleatórias — os pesos foram aprendidos para a escala [-1,1] e receber [0,1] gera ativações completamente fora do esperado
D
O modelo retorna um erro indicando normalização incorreta
✅ Alternativa C. Os pesos de uma rede neural aprendem padrões na escala exata dos dados de treino. Um pixel 255 (branco) normalizado para [-1,1] dá 1.0; normalizado para [0,1] dá 1.0 também — mas um pixel 0 (preto) dá -1.0 vs 0.0, e pixels intermediários diferem drasticamente. As ativações de todas as camadas ficam fora do range esperado, resultando em probabilidades distribuídas de forma quase aleatória.

Sem. 11
Por que o Transformers.js usa o formato ONNX em vez de carregar pesos PyTorch (.pt) diretamente no browser?
A
ONNX comprime os pesos automaticamente — modelos ficam 10x menores
B
PyTorch não roda no browser — ONNX é um formato neutro executável pelo ONNX Runtime Web via WebAssembly/WebGL sem precisar do Python runtime
C
ONNX é um requisito de licença — HuggingFace só distribui modelos no browser em formato ONNX
D
É apenas uma preferência — PyTorch funcionaria igual no browser com um polyfill
✅ Alternativa B. PyTorch depende do runtime Python, CUDA e do ecossistema científico C++/Python para funcionar — nada disso existe no browser. ONNX (Open Neural Network Exchange) é um formato aberto de representação de modelos que pode ser executado por engines independentes. O ONNX Runtime Web roda em WebAssembly (fallback CPU) ou WebGL/WebGPU (acelerado GPU) — disponíveis em browsers modernos sem instalar nada.

Um componente usa três useState: isLoading, isError e data. Qual é o principal problema dessa abordagem para estados de operação assíncrona?
A
O componente re-renderiza três vezes a cada atualização — um por setState chamado
B
Estados impossíveis podem existir — isLoading=true e isError=true simultaneamente é tecnicamente possível e causa bugs difíceis de rastrear
C

Questão Dissertativa 1 — Semanas 7 e 8
Você precisa construir um chatbot que exibe as respostas da IA com formatação markdown e efeito de digitação token a token. Descreva: (a) por que usar fetch com ReadableStream em vez de EventSource, (b) o que deve aparecer durante o stream (texto puro ou markdown renderizado) e por quê, e (c) por que react-markdown é mais seguro que marked() com dangerouslySetInnerHTML.
(a) fetch vs EventSource: EventSource é a API nativa de SSE do browser, mas só faz requisições GET e não permite customizar headers. A API da OpenAI exige um POST (para enviar body com mensagens e parâmetros como model, temperature, stream:true) e o header Authorization: Bearer TOKEN. EventSource simplesmente não suporta esse requisito. A solução é fetch com a opção de leitura incremental: response.body.getReader() retorna um ReadableStream que pode ser lido chunk a chunk com reader.read(), enquanto o TextDecoder converte os bytes em texto SSE.

(b) Durante o stream — texto puro, não markdown: durante a geração, o markdown está incompleto. Um bloco de código que ainda não fechou o ``` faz o parser de markdown "engolir" o texto seguinte como código, causando artefatos visuais: títulos onde deveria ter texto, listas onde deveria ter parágrafo. O melhor padrão é exibir o texto crescente com white-space: pre-wrap e fonte monospace (dá sensação de "digitação de terminal"), e só renderizar com ReactMarkdown depois que o stream completa e a mensagem é adicionada ao histórico. Esse é o comportamento do Claude e do ChatGPT.

(c) react-markdown vs dangerouslySetInnerHTML: marked() converte markdown para HTML — uma string com tags HTML. dangerouslySetInnerHTML injeta essa string diretamente no DOM sem qualquer sanitização. Se o LLM retornar <script>alert(document.cookie)</script> como parte da resposta, esse script será executado no browser do usuário — isso é XSS (Cross-Site Scripting). react-markdown, por outro lado, analisa o markdown e o converte em componentes React — nunca em HTML cru. Scripts e tags perigosas nunca chegam ao DOM como HTML executável; são serializados como texto.
Questão Dissertativa 2 — Semanas 9 e 10
Um time de ML quer um dashboard que exibe: (a) a curva de treinamento de um modelo (accuracy e loss por época), (b) precision e recall por classe, e (c) distribuição das predições. Para cada um, indique qual tipo de gráfico Recharts usar e por quê. Adicione também: como você detectaria overfitting visualizando o dashboard?
(a) Curva de treinamento → LineChart: a pergunta é "como X muda ao longo do tempo (épocas)?" — esse é o caso de uso clássico do gráfico de linha. O dado tem uma dimensão temporal (época no XAxis) e duas séries numéricas (accuracy e loss, cada uma com seu dataKey). Para diferenciar treino de validação, adiciona-se mais duas linhas com strokeDasharray para as curvas de validação.

(b) Precision e recall por classe → BarChart: a pergunta é "como X se compara a Y e Z por categoria?" — comparação entre categorias é o caso de uso do gráfico de barras. O dado tem as classes no XAxis (dataKey="classe") e três séries no YAxis: precision, recall e f1 — cada uma como um Bar com dataKey próprio. Isso permite ver imediatamente quais classes têm métricas baixas.

(c) Distribuição das predições → PieChart com innerRadius: a pergunta é "qual é a proporção de cada categoria?" — proporção de partes de um todo é o caso do donut. Com innerRadius > 0, o percentual dominante pode ser exibido no centro. Com apenas 3–5 classes, o donut é legível; com mais fatias, BarChart seria mais adequado.

Detectando overfitting no dashboard: no LineChart da curva de treinamento, overfitting fica visível quando a linha de accuracy (treino) continua subindo mas a linha de val_accuracy (validação, geralmente com strokeDasharray) para de subir e começa a descer — ou quando a linha de loss cai mas val_loss sobe. O ponto de cruzamento é o epoch ótimo. Em uma tabela de números, identificar isso requer comparar linha por linha; no gráfico, o padrão é imediatamente visível.
Questão Dissertativa 3 — Semanas 10 e 11
Compare TensorFlow.js (Semana 10) e Transformers.js (Semana 11) em termos de: (a) tipos de tarefas para os quais cada um é adequado, (b) como cada um gerencia memória no browser, e (c) por que Transformers.js exige Web Worker enquanto TensorFlow.js tolera rodar na thread principal para inferências pontuais.
(a) Tarefas adequadas: TensorFlow.js é ideal para visão computacional (classificação de imagem com MobileNet, detecção de objetos com COCO-SSD, estimação de pose), manipulação de tensores matemáticos e modelos customizados exportados do Keras. Transformers.js brilha em NLP (sentimento, NER, tradução, embeddings, geração de texto) — modelos baseados na arquitetura Transformer do HuggingFace. As bibliotecas não são competidoras: TF.js domina visão, Transformers.js domina texto.

(b) Gerenciamento de memória: TensorFlow.js usa WebGL buffers na GPU — completamente fora do heap JavaScript e invisíveis ao GC. Toda memória deve ser liberada manualmente com .dispose() ou encapsulada em tf.tidy() que descarta automaticamente os tensores intermediários ao terminar. tf.memory().numTensors monitora leaks em tempo real. Transformers.js usa o ONNX Runtime Web que gerencia sua própria memória interna — o desenvolvedor não precisa chamar dispose() explicitamente, mas deve carregar o modelo apenas uma vez (em Worker) para não duplicar o download e uso de memória.

(c) Thread principal vs Web Worker: uma inferência com MobileNet para uma imagem leva ~50–100ms — rápido o suficiente para não ser perceptível em uma interação pontual (clique em botão). Uma inferência com DistilBERT para análise de sentimento leva ~100–300ms e, mais importante, pode ser chamada com alta frequência (debounce de 400ms enquanto o usuário digita), acumulando bloqueios. Modelos Transformer têm mais operações de atenção e são mais pesados por token. O Web Worker é obrigatório para Transformers.js porque a inferência deve acontecer continuamente sem jamais congelar a UI — cada tecla pressionada aciona uma análise.
Questão Dissertativa 4 — Semana 12
Um chatbot de IA para suporte ao cliente recebe um erro 500 da API, um usuário pergunta sobre dosagem de medicamento e a conversa acumulou 3.800 tokens de um limite de 4.096. Descreva como o front-end deve tratar cada uma dessas três situações usando os padrões de UX da Semana 12.
Erro 500 (internal server error): o reducer despacha {tipo:'ERRO'} com o resultado de traduzirErro(). Para status 500, a mensagem deve ser: "O serviço está com instabilidade no momento. Tente novamente em alguns instantes." — um ícone de servidor ou alerta, título amigável, descrição sem jargão técnico. O componente EstadoErro exibe um botão "Tentar novamente" que re-executa a última requisição, opcionalmente com retry automático após 5 segundos (contador regressivo visível). Nunca exibir "Error 500: Internal Server Error" para o usuário.

Pergunta sobre dosagem de medicamento: detectar a presença de palavras-chave críticas na resposta gerada (medicamento, dosagem, remédio, tratamento, diagnóstico). Ao identificar, adicionar automaticamente abaixo da mensagem o componente Disclaimer com role="note": "⚠ Esta resposta é informativa. Para decisões de saúde, consulte um médico ou farmacêutico habilitado." O disclaimer não substitui a resposta — é aditivo. Em casos extremamente sensíveis (suicídio, emergência médica), pode-se implementar um filtro no prompt que instrui o modelo a sempre incluir referência a serviços de emergência.

3.800 de 4.096 tokens (93% do contexto): exibir o componente AvisoContextoLongo com role="alert" e aria-live="assertive" — o leitor de tela anuncia o aviso. A mensagem: "🧠 Conversa usando 93% do contexto disponível. Inicie uma nova conversa para continuar com qualidade." Com um botão "Nova conversa" proeminente. A estimativa de tokens é feita contando palavras × 1.3 (fator de aproximação). Ao atingir 100%, a próxima mensagem falhará com erro 400 (context length exceeded) — antecipe com o aviso antes de chegar lá.

Como a P2 funciona — formato, critérios e estratégia
Atenção: a P2 é prova fechada — sem consulta. Abrange streaming (S7), markdown (S8), gráficos (S9), TF.js (S10), Transformers.js (S11) e UX (S12). A prova prática pode envolver qualquer combinação dessas tecnologias em um único componente.
Formato e critérios
ParteTipoO que é avaliado

Parte 2DissertativaComparação de tecnologias, justificativa de escolha arquitetural, fluxo completo

Diferencial em dissertativa: "usar useReducer para evitar estados impossíveis como loading=true e error=true ao mesmo tempo" pontua muito mais que "useReducer é melhor que useState". Seja específico, use termos técnicos e nomeie os estados, ações e transições.
Estratégia para a parte prática
01
Identifique a tecnologia central
Leia o enunciado e identifique: streaming (ReadableStream), gráfico (Recharts + dados), ML client-side (TF.js ou Transformers.js) ou UX (useReducer + skeleton). A tecnologia central dita a estrutura do código.
02
Declare os estados primeiro
Para streaming: status, respostaAtual, histórico, abortRef. Para gráfico: dados, carregando. Para UX: useReducer com os 4 estados. Ter os estados claros antes de escrever JSX evita erros estruturais.
03
Palavras-chave do enunciado
"sem travar a UI" → Web Worker. "dados sensíveis" → client-side ML. "exibir formatado" → react-markdown. "erro amigável" → traduzirErro(). "cancelar" → AbortController. "loading state" → skeleton + useReducer.
04
Código incompleto com comentários explicando o restante pontua mais que código completo sem lógica. Demonstre que você entende o fluxo mesmo que não lembre a sintaxe exata de uma função.
