Revisão rápida
Os 4 temas — pontos-chave e armadilhas comuns
Semana 14 — Acessibilidade (a11y)
WCAG 2.1 POUR: Perceptível, Operável, Compreensível, Robusto — níveis A, AA, AAA
Contraste (1.4.3): ≥ 4.5:1 para texto normal, ≥ 3:1 para texto grande
ARIA em IA: aria-live="polite" + role="log" no histórico, role="status" no skeleton, role="alert" em erros
Foco visível: :focus-visible em vez de :focus — nunca outline:none sem substituto
sr-only: esconde visualmente mas mantém para leitor de tela — nunca display:none para isso
prefers-reduced-motion: desativa shimmer/cursor piscante para quem tem essa preferência ativada
Armadilha: aria-label em botão de emoji sem pensar no aria-pressed para toggles (👍/👎) — o estado "pressionado" também precisa ser comunicado.
Semana 15 — Performance
Core Web Vitals: LCP ≤ 2.5s, INP ≤ 200ms, CLS ≤ 0.1
INP em apps de IA: inferência na thread principal bloqueia a UI — usar Web Worker
Code splitting: React.lazy() + Suspense para componentes pesados (syntax-highlighter, recharts, TF.js)
Importação seletiva: importar só o tema do syntax-highlighter usado economiza centenas de KB
Caching de modelos: IndexedDB para TF.js, cache automático do browser para Transformers.js
useMemo/useCallback: só compensam para cálculos caros com re-render frequente
Armadilha: achar que useMemo/useCallback devem ser usados em todo lugar — o custo de comparação de dependências pode superar o ganho em casos simples.
Semana 16 — Estado Global
Limite do Context: todo consumidor re-renderiza quando qualquer parte do value muda
Zustand: sem Provider, seletores granulares evitam re-render desnecessário
persist + partialize: escolhe o que é salvo, excluindo estado transitório (ex: streaming:true)
Redux Toolkit: createSlice + Immer permitem "mutação" segura dentro de reducers
Zustand vs RTK: Zustand para projetos ágeis/pequenos; RTK para times grandes com mais convenção
IndexedDB: alternativa ao localStorage para históricos muito grandes (limite maior, assíncrono)
Armadilha: persistir campos transitórios (ex: streaming, loading) faz a UI mostrar um estado "congelado" incorreto após reload.
Semana 17 — Testes
Pirâmide de testes: muitos unitários, camada média de integração, poucos E2E
Nunca chamar API real: não-determinismo, custo e dependência de rede/API key quebram a suíte
RTL: testar comportamento (o que o usuário vê/faz), não implementação interna
getByRole > getByTestId: reflete o que tecnologia assistiva percebe — falha revela problema de a11y
jest.mock vs MSW: jest.mock troca o módulo JS; MSW intercepta na camada de rede, mais realista
waitFor: necessário para asserções sobre UI que atualiza de forma assíncrona
Armadilha: perseguir 100% de cobertura em vez de priorizar os caminhos críticos (envio, erro, retry, acessibilidade).

Um texto secundário em uma interface dark tem contraste calculado de 3.1:1 contra o fundo. Isso passa no critério WCAG 2.1 AA de Contraste Mínimo (1.4.3) para texto normal?
A
Sim, pois qualquer contraste acima de 3:1 já é considerado acessível
B
Não, o critério 1.4.3 exige ≥ 4.5:1 para texto normal — 3.1:1 falha
C
Depende do tamanho da fonte — qualquer fonte acima de 12px aceita 3:1
D
Sim, pois o critério de contraste só se aplica a botões, não a texto secundário
✅ Alternativa B. O critério 1.4.3 (Contraste Mínimo, nível AA) exige razão ≥ 4.5:1 para texto normal (abaixo de 18pt ou 14pt em negrito) e ≥ 3:1 apenas para texto grande. 3.1:1 falha para texto normal — é um valor comum em textos "secundários" ou "muted" de interfaces dark, e uma das violações mais frequentes encontradas em auditorias com axe DevTools.

Semana 14
Um chatbot exibe novos tokens em uma <div> comum, sem nenhum atributo ARIA. Um usuário de NVDA não ouve nada quando a resposta chega. Qual mudança resolve isso?
A
Adicionar tabindex="0" na div para torná-la focável
B
Adicionar role="log" e aria-live="polite" na div do histórico
C
Adicionar aria-label="mensagem" em cada bubble individual
D
Trocar a div por um <button>
✅ Alternativa B. aria-live="polite" instrui o leitor de tela a anunciar mudanças de conteúdo naquela região sem interromper o que o usuário está fazendo. role="log" complementa indicando que é uma região de mensagens que recebe adições ao final. Semana 15
Um chatbot tem INP de 700ms sempre que o usuário clica em "Enviar" enquanto usa Transformers.js. Qual é a causa mais provável e a correção?
A
Bundle grande demais — corrigir com code splitting apenas
B
Inferência rodando na thread principal, bloqueando a atualização da UI — mover para um Web Worker
C
Latência de rede até o servidor de IA — usar um CDN mais próximo
D
CLS alto — adicionar min-height nos elementos
✅ Alternativa B. INP (Interaction to Next Paint) mede o tempo entre a interação e o próximo frame pintado. Quando a inferência de um modelo roda na thread principal, ela bloqueia toda a JavaScript engine — incluindo a atualização visual que mostraria feedback do clique. A solução correta (vista na Semana 11 e reforçada na 15) é mover a inferência para um Web Worker, liberando a thread principal para responder à UI imediatamente.

Semana 15
Por que importar apenas um tema específico do react-syntax-highlighter (em vez do pacote de temas completo) reduz tanto o tamanho do bundle?
A
Porque o React comprime automaticamente imports não utilizados em tempo de execução
B
Porque a importação completa inclui dezenas de temas não usados; importar só o necessário evita empacotar código morto no bundle final
C
Porque temas de syntax highlight são carregados via streaming, independente do import
D
Não há diferença real de tamanho, apenas de organização do código
✅ Alternativa B. O pacote completo de temas do react-syntax-highlighter empacota todos os temas disponíveis (dezenas deles) no bundle, mesmo que o app só use um. Importar diretamente o caminho do tema específico (ex: from 'react-syntax-highlighter/dist/esm/styles/prism') permite que o bundler inclua só aquele arquivo, evitando ~840KB de código morto — um dos ajustes de maior impacto/esforço vistos na Semana 15.

Semana 16
Um componente Sidebar lê apenas useChatStore(estado => estado.tema). Uma nova mensagem chega e é adicionada ao array mensagens na mesma store. A Sidebar re-renderiza?
A
Sim, toda mudança na store re-renderiza todos os componentes que a usam, como no Context
B
Não, porque o seletor só observa "tema", que não mudou — o Zustand compara o retorno do seletor entre renders
C
Só se houver um Provider envolvendo a Sidebar
D
Depende de a store usar o middleware persist ou não
✅ Alternativa B. Essa é a diferença central entre Zustand e Context API: o seletor passado a useChatStore extrai só a fatia desejada, e o Zustand compara esse valor entre o estado antigo e o novo. Como "tema" não mudou, não há re-render — mesmo que outra parte da store (mensagens) tenha mudado. Zustand também não usa Provider, então a opção C está incorreta por dois motivos.

Semana 16
Por que o campo streaming (booleano indicando se uma resposta está sendo gerada) deve ser excluído do partialize de uma store Zustand com persist?
A
Porque booleanos não podem ser serializados em JSON
B
Porque é estado transitório da sessão — persistir "true" faria a UI parecer travada em "gerando resposta" após um reload, mesmo sem requisição real em andamento
C
Porque o localStorage tem uma cota específica só para booleanos
D
Não há motivo técnico — é apenas uma escolha estética
✅ Alternativa B. partialize decide o que sobrevive a um reload. Campos que refletem "algo está acontecendo agora" (streaming, um AbortController em andamento) perdem sentido depois que a página recarrega — a requisição real já foi perdida. Se persistidos, a UI mostraria um estado inconsistente com a realidade (ex: "gerando resposta..." para sempre, sem nenhuma requisição ativa por trás).

Semana 17
Por que os testes de front-end de um chatbot de IA nunca devem chamar a API real da OpenAI durante a suíte?
A
Porque o Jest bloqueia tecnicamente qualquer chamada de rede
B
Porque a resposta é não-determinística, a chamada é lenta e custa dinheiro a cada execução, além de amarrar a suíte a uma conexão de rede e credenciais válidas
C
Porque APIs de IA bloqueiam User-Agents de ferramentas de teste automaticamente
D
Não há problema real nisso, é só uma convenção sem justificativa técnica
✅ Alternativa B. O motivo é uma combinação de três fatores: não-determinismo (o texto muda a cada chamada, impossibilitando expect().toBe() confiável), custo real (cada execução da suíte em CI gera uma chamada cobrada) e dependência externa (rede e API key, que quebram a suíte em ambientes sem credenciais). A prática correta é sempre mockar a camada de IA com jest.mock ou MSW.

Semana 17
Qual a diferença entre mockar com jest.mock('./api/chamarIA') e usar MSW (Mock Service Worker) para a mesma chamada?
A
Não há diferença — são a mesma técnica com nomes diferentes
B
jest.mock substitui o módulo JS inteiro; MSW intercepta a requisição na camada de rede, então o código real de fetch continua sendo executado e testado
C
MSW só funciona com Axios, nunca com fetch nativo
D
jest.mock é mais lento porque inicia um servidor de verdade
✅ Alternativa B. jest.mock troca a função inteira — o código real de fetch dentro dela nunca roda. MSW opera uma camada abaixo: intercepta a requisição HTTP em si, deixando o código real de fetch/axios do app ser exercitado de verdade, com apenas a resposta do "servidor" sendo fake. Isso torna o teste mais fiel ao comportamento real em produção.

Quando faz mais sentido escolher Redux Toolkit em vez de Zustand para um projeto de front-end de IA?
A
Sempre — Redux Toolkit é estritamente superior em qualquer cenário

Questão Dissertativa 1 — Semana 14
Explique por que interfaces de IA com conteúdo dinâmico (streaming de respostas, skeletons de carregamento) apresentam desafios específicos de acessibilidade que interfaces estáticas não têm. Cite pelo menos três padrões ARIA que resolvem esses desafios e o que cada um comunica a um leitor de tela.
Interfaces estáticas têm seu conteúdo totalmente presente quando a página carrega — um leitor de tela consegue navegar e ler tudo de forma previsível. Interfaces de IA quebram essa previsibilidade: o conteúdo aparece progressivamente (streaming), muda de estado sem ação explícita do usuário (loading → sucesso/erro), e usa elementos visuais sem texto (emojis em botões, skeletons animados) que não têm significado semântico por padrão.

role="log" + aria-live="polite" no container do histórico: comunica que aquela região recebe novas mensagens ao final e que o leitor deve anunciá-las sem interromper agressivamente o que o usuário está fazendo — essencial porque, sem isso, tokens chegando via streaming são completamente silenciosos.

role="status" no skeleton loader: informa que aquela região está em atualização/carregamento, permitindo que o leitor comunique "carregando" de forma discreta, sem soar como um alerta urgente.

role="alert" nos estados de erro: ao contrário do role="status", interrompe o usuário imediatamente — apropriado para falhas que exigem atenção, como um erro de rate limit ou de rede.

aria-label em botões de emoji (👍/👎): sem ele, o leitor de tela só anuncia "botão", sem contexto nenhum sobre a função. Complementado por aria-pressed quando o botão é um toggle, para comunicar o estado selecionado.
Questão Dissertativa 2 — Semanas 15 e 16
Um chatbot apresenta INP alto (acima de 500ms) sempre que uma nova mensagem chega, mesmo com a inferência de IA rodando em um Web Worker. Ao investigar com React DevTools Profiler, você descobre que o componente Sidebar (que só exibe o tema atual) está re-renderizando a cada token do streaming. Explique a causa provável e a correção, conectando os conceitos de Context API, Zustand e performance de re-render.
Causa provável: se o app ainda usa Context API para gerenciar tanto o histórico de mensagens quanto o tema (um único ChatContext, por exemplo), qualquer atualização no value do Provider — mesmo que seja só o array de mensagens crescendo com o streaming — recria o objeto de value inteiro. Todo componente que consome esse Context via useContext re-renderiza, independentemente de qual fatia específica ele usa. A Sidebar, mesmo lendo só "tema", é arrastada nesse re-render em cascata porque ela está inscrita no Context inteiro, não em uma fatia dele.

Por que isso afeta o INP: mesmo com a inferência isolada em um Web Worker (resolvendo o bloqueio da thread principal durante o cálculo), re-renders desnecessários e frequentes de componentes não relacionados ainda consomem tempo de CPU na thread principal a cada token — múltiplos desses re-renders acumulados podem, juntos, degradar o INP percebido, especialmente em dispositivos mais fracos.

Correção: migrar o estado para uma store Zustand com seletores granulares. A Sidebar passaria a usar useChatStore(estado => estado.tema) — o Zustand compara esse valor específico entre renders e só dispara re-render se "tema" de fato mudou, ignorando completamente as atualizações do array de mensagens. Isso elimina o re-render em cascata característico da Context API e reduz o trabalho da thread principal a cada token do streaming.
Questão Dissertativa 3 — Semana 17
Escreva (em pseudocódigo ou código real) um teste de integração usando React Testing Library e MSW para o cenário: o usuário digita uma mensagem, pressiona Enter, a API de IA (mockada) retorna um erro 429, e a interface deve exibir uma mensagem amigável com um botão "Tentar novamente". Explique por que esse teste NÃO deveria verificar o texto exato retornado por uma chamada real de IA.
React — teste de integração para o cenário de rate limit
test('exibe erro amigável e botão de retry em rate limit (429)', async () => {
  server.use(
    http.post('/api/chat', () => new HttpResponse(null, { status: 429 }))
  );

  const user = userEvent.setup();
  render(<Chatbot />);

  await user.type(screen.getByRole('textbox'), 'oi{Enter}');

  await waitFor(() => {
    expect(screen.getByText(/muitas mensagens em pouco tempo/i)).toBeInTheDocument();
  });
  expect(screen.getByRole('button', { name: /tentar novamente/i })).toBeInTheDocument();
});
Por que não verificar texto exato de uma chamada real de IA: respostas de LLMs são não-determinísticas por natureza — a mesma pergunta pode gerar respostas diferentes em chamadas distintas, mesmo com temperature=0 em alguns modelos. Um teste com expect(texto).toBe("resposta exata") contra uma chamada real seria frágil e falharia aleatoriamente sem relação com um bug real no código. O teste deve validar o comportamento da interface diante de diferentes respostas simuladas — se o app mostra a bubble corretamente quando a IA responde X, se trata o erro Y corretamente — nunca o conteúdo específico gerado pelo modelo em si.
Questão Dissertativa 4 — Revisão geral (Semanas 14 a 18)
Descreva o "fio condutor" que conecta Acessibilidade (S14), Performance (S15), Estado Global (S16), Testes (S17) e Deploy/CI-CD (S18) em um único projeto de front-end de IA. Por que faz sentido tratá-los como uma cadeia de qualidade, e não como tópicos isolados?
Cada uma dessas semanas resolve um risco específico de um app de IA em produção, e cada risco resolvido em uma semana só se sustenta de verdade quando as semanas seguintes o automatizam e verificam continuamente.

Acessibilidade (S14) garante que a interface funcione para usuários com deficiência, mas depende de disciplina manual para não regredir a cada mudança de código. Performance (S15) garante velocidade, mas da mesma forma pode degradar silenciosamente com o tempo se ninguém monitorar. Estado Global (S16) resolve como a aplicação gerencia dados complexos (histórico de conversas, configurações) de forma confiável e persistente — mas um bug de re-render ou de persistência mal configurada só é pego com atenção ativa.

É aqui que Testes (S17) entram: eles transformam "eu verifiquei manualmente que funciona" em "há uma verificação automática de que continua funcionando", cobrindo os comportamentos de a11y (via getByRole), performance de re-render (indiretamente, testando a store) e o fluxo de erro/retry.

Mas testes que só rodam quando alguém lembra de executá-los manualmente também não escalam — por isso Deploy/CI-CD (S18) fecha o ciclo: GitHub Actions garante que os testes da S17 rodem em toda Pull Request, e o Lighthouse CI garante que os scores de Performance (S15) e Acessibilidade (S14) sejam checados automaticamente antes de qualquer código chegar à produção. O Estado Global bem configurado (S16) é validado na prática quando o app publicado (S18) mantém o histórico após um F5 real, em produção.

Tratar esses temas isoladamente perde essa cadeia: a11y sem testes automatizados regride silenciosamente; testes sem CI dependem de disciplina humana; performance sem Lighthouse CI não tem um portão de qualidade. Juntos, formam um pipeline onde cada camada verifica e sustenta a anterior.
