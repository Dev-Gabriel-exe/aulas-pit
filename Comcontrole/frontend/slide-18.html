Deploy na Vercel — do repositório Git ao app no ar
Como a Vercel transforma um push em um deploy

A Vercel é a plataforma de deploy mais usada para projetos React/Next.js. O fluxo básico: você conecta um repositório GitHub, a Vercel detecta automaticamente o framework (Vite, Next.js, CRA), executa o build e publica o resultado em uma URL pública. Cada novo git push dispara um novo deploy automaticamente.

Buildnpm install + npm run build
DeployURL pública gerada
Tipo de deployQuando aconteceURL geradaUso típico
ProductionPush/merge na branch principal (main)seu-projeto.vercel.app (ou domínio customizado)A versão que os usuários finais acessam
PreviewPush em qualquer outra branch ou Pull RequestURL única por commit (ex: seu-projeto-git-feature-x.vercel.app)Testar uma feature antes de mesclar, compartilhar com o professor/cliente para revisão

Por que Preview Deployments mudam o fluxo de trabalho: antes de mesclar uma Pull Request, cada commit já gera uma URL funcional e isolada. Isso significa que você pode testar uma nova feature do chatbot (ex: um novo modelo de IA) em produção real, sem afetar o app que os outros usuários estão usando — e compartilhar o link para revisão antes do merge.

Variáveis de ambiente em produção — fechando o ciclo da Semana 5
Do .env local ao dashboard da Vercel

Na Semana 5, você aprendeu que a chave de API nunca deve ficar hardcoded no código, e sim em um arquivo .env ignorado pelo Git. Em produção, esse arquivo não existe no servidor — as variáveis são configuradas diretamente no dashboard da Vercel, por ambiente (Production, Preview, Development).

Errado — chave exposta no front
Uma variável como VITE_OPENAI_KEY ou REACT_APP_OPENAI_KEY é embutida no bundle JavaScript no momento do build — qualquer usuário pode abrir o DevTools e ver a chave, mesmo em produção na Vercel.
Certo — chave só no servidor
A chave fica em uma variável sem o prefixo VITE_/REACT_APP_ (ex: OPENAI_API_KEY), usada apenas dentro de uma API Route/Serverless Function da Vercel. O bundle do cliente nunca a recebe.
A armadilha do prefixo: em projetos Vite, qualquer variável de ambiente prefixada com VITE_ é injetada no bundle do cliente por design — é assim que o Vite decide o que é seguro expor ao browser. O mesmo vale para REACT_APP_ no Create React App e NEXT_PUBLIC_ no Next.js. Se a chave da OpenAI usar esse prefixo, ela SEMPRE vai parar no bundle público, não importa onde ela esteja configurada no dashboard da Vercel.
JavaScript — API Route da Vercel usando a chave com segurança
// api/chat.js — Serverless Function da Vercel (roda no servidor, nunca no browser)
export default async function handler(req, res) {
  if (req.method !== 'POST') {
    return res.status(405).json({ erro: 'Método não permitido' });
  }

  // process.env.OPENAI_API_KEY — SEM prefixo VITE_/NEXT_PUBLIC_
  // Essa variável só existe no ambiente do servidor, nunca chega ao cliente
  const resposta = await fetch('https://api.openai.com/v1/chat/completions', {
    method: 'POST',
    headers: {
      'Authorization': `Bearer ${process.env.OPENAI_API_KEY}`,
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({
      model: 'gpt-4o-mini',
      messages: req.body.mensagens,
    }),
  });

  const dados = await resposta.json();
  res.status(200).json(dados);
}

// No front-end, o app chama SEU PRÓPRIO endpoint, nunca a OpenAI diretamente:
const res = await fetch('/api/chat', {
  method: 'POST',
  body: JSON.stringify({ mensagens }),
});

GitHub Actions e Lighthouse CI — qualidade automatizada a cada push
GitHub Actions — rodando os testes da Semana 17 automaticamente

CI/CD significa Integração Contínua (Continuous Integration) e Entrega/Deploy Contínuo (Continuous Delivery/Deployment). GitHub Actions permite definir workflows — sequências de passos automatizados que rodam a cada push ou Pull Request, como instalar dependências, rodar a suíte de testes e fazer build.

YAML — .github/workflows/ci.yml
name: CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout do código
        uses: actions/checkout@v4

      - name: Configurar Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Instalar dependências
        run: npm ci

      - name: Rodar testes
        run: npm test -- --coverage

      - name: Build de produção
        run: npm run build

# Com esse workflow, uma Pull Request só pode ser mesclada se:
# 1. npm ci não falhar (dependências instalam corretamente)
# 2. npm test não falhar (todos os testes da Semana 17 passam)
# 3. npm run build não falhar (o projeto compila sem erros)
# O GitHub mostra um ✓ verde ou ✗ vermelho diretamente na PR
Por que isso muda tudo: sem CI, é possível mesclar código quebrado na branch principal por descuido — um teste que falha localmente mas ninguém rodou antes do commit. Com o workflow acima, o GitHub bloqueia visualmente o merge (ou ao menos avisa claramente) se qualquer teste da Semana 17 falhar. A suíte de testes só tem valor real quando ela roda automaticamente, não quando depende de alguém lembrar de rodar npm test manualmente.
Lighthouse CI — auditoria de performance e acessibilidade automatizada

A Semana 14 (a11y) e a Semana 15 (performance) ensinaram a rodar o Lighthouse manualmente no DevTools. O Lighthouse CI automatiza essa auditoria: roda a cada push, compara com um histórico de scores, e pode falhar o build se a pontuação cair abaixo de um limite definido — evitando que uma regressão de performance ou acessibilidade passe despercebida.

YAML — adicionando Lighthouse CI ao workflow
# lighthouserc.json — configuração dos limites mínimos aceitos
{
  "ci": {
    "collect": {
      "staticDistDir": "./dist",
      "numberOfRuns": 3
    },
    "assert": {
      "assertions": {
        "categories:performance": ["error", {"minScore": 0.85}],
        "categories:accessibility": ["error", {"minScore": 0.9}]
      }
    }
  }
}

# Job adicional no .github/workflows/ci.yml
- name: Lighthouse CI
  run: |
    npm install -g @lhci/cli
    lhci autorun

# Se "categories:performance" cair abaixo de 0.85 (85), o job falha
# e a PR mostra um X vermelho — igual a um teste que falhou.
# Isso transforma o Lighthouse de "checagem manual esquecível"
# em um portão de qualidade automático do projeto.

B

4 exercícios — de rollback a monorepo
Exercício 01 — Rollback de um deploy com problema

Um deploy recente introduziu um bug crítico em produção (o botão de enviar parou de funcionar). Pesquise e descreva o processo de rollback na Vercel: como reverter instantaneamente para o último deploy estável sem precisar reverter o commit no Git primeiro. Explique por que isso é mais rápido que um git revert + novo deploy.

Conceito
Na Vercel, cada deploy fica arquivado e acessível permanentemente (a menos que seja excluído manualmente). No dashboard, em Deployments, cada entrada tem um botão "Promote to Production" (ou "Instant Rollback" em planos com esse recurso) que aponta o domínio de produção diretamente para um deploy anterior já buildado — sem rodar um novo build.

Isso é mais rápido que git revert porque: (1) não depende de re-executar npm install e npm run build — o artefato já existe pronto; (2) elimina o risco de o build do revert falhar por algum motivo externo (dependência que mudou de versão, por exemplo); (3) leva segundos, enquanto um novo ciclo completo de CI/CD pode levar minutos. O revert no Git ainda deve ser feito depois, para que o histórico do repositório reflita a correção — mas ele não precisa bloquear a recuperação imediata da produção.
Exercício 02 — Workflow de CI que só faz build em Pull Requests

Modifique o workflow ci.yml da Aula 3 para que o job de testes rode em toda Pull Request e todo push na main, mas o job de Lighthouse CI rode apenas em Pull Requests (não em pushes diretos na main) — evitando gastar minutos de CI desnecessariamente em merges já testados anteriormente.

GitHub Actions
YAML — workflow com jobs condicionais por evento
name: CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20' }
      - run: npm ci
      - run: npm test
      - run: npm run build

  lighthouse:
    # Roda SÓ em Pull Requests — condição verifica o evento que disparou o workflow
    if: github.event_name == 'pull_request'
    needs: test  # só roda se o job "test" passou primeiro
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20' }
      - run: npm ci && npm run build
      - run: npx @lhci/cli autorun
Exercício 03 — Comentário automático do score Lighthouse na PR

Pesquise e configure a ação treosh/lighthouse-ci-action (ou similar) para que o resultado do Lighthouse CI seja postado automaticamente como um comentário na Pull Request, mostrando os 4 scores (Performance, Acessibilidade, Boas Práticas, SEO) sem que ninguém precise abrir os logs do GitHub Actions manualmente.

GitHub Actions
YAML — comentário automático de Lighthouse na PR
- name: Lighthouse CI com comentário na PR
  uses: treosh/lighthouse-ci-action@v11
  with:
    urls: |
      https://chatbot-ia-git-${{ github.head_ref }}.vercel.app
    uploadArtifacts: true
    temporaryPublicStorage: true

# Essa action:
# 1. Roda o Lighthouse contra a URL de Preview daquele Pull Request específico
#    (a URL segue o padrão de branch da Vercel)
# 2. Publica os relatórios em um storage temporário público
# 3. Comenta automaticamente na PR com os 4 scores e um link para o relatório completo
# Isso elimina a necessidade de qualquer pessoa abrir os logs brutos do
# GitHub Actions para saber se a performance regrediu — a informação
# aparece diretamente onde a revisão de código já está acontecendo.
Exercício 04 — Desafio: domínio customizado com preview de branches de feature

Configure um domínio customizado (pode ser gratuito, tipo .vercel.app mesmo, ou um domínio real se tiver) e explore o recurso de Vercel de gerar automaticamente uma URL de preview estável por nome de branch (ex: sempre a mesma URL para a branch feature/novo-modelo, mesmo com múltiplos commits). Documente como isso ajuda um time a compartilhar links fixos durante o desenvolvimento de uma feature de IA ao longo de vários dias.

Desafio · Configuração
A Vercel gera uma URL de preview por branch no formato projeto-git-nome-da-branch-usuario.vercel.app, que permanece estável entre commits — cada novo push na mesma branch atualiza o conteúdo servido nessa mesma URL, em vez de gerar uma URL nova a cada commit (essa é a diferença entre a "branch URL" e a "commit URL", ambas geradas pela Vercel).

Para um time trabalhando em uma feature de IA por vários dias (ex: testar um novo modelo ou um novo fluxo de streaming), isso significa: (1) o link pode ser compartilhado uma única vez com o professor/cliente/QA no início do trabalho; (2) cada novo commit na branch atualiza automaticamente o que essa pessoa vê, sem precisar reenviar um novo link a cada mudança; (3) a comparação lado a lado com a produção fica trivial — duas abas, duas URLs, o mesmo app em dois estados. Isso reduz drasticamente o atrito de dar e receber feedback durante o desenvolvimento incremental de uma feature.
