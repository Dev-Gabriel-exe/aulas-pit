Quem são os usuários que acessibilidade impacta

Acessibilidade não é um recurso extra para uma minoria — é uma necessidade que afeta a maioria das pessoas em algum momento da vida. Uma interface inacessível exclui: usuários com deficiência visual (cegos, baixa visão, daltonismo), deficiência motora (navegam só com teclado), deficiência auditiva (dependem de legendas) e deficiência cognitiva (beneficiam-se de linguagem clara e estrutura previsível).

Em interfaces de IA, os problemas mais comuns surgem exatamente onde o conteúdo é dinâmico e imprevisível: uma resposta que aparece token a token não é anunciada por leitores de tela sem aria-live. Um botão "👍" sem aria-label é completamente invisível para quem usa leitor de tela. Um skeleton sem role="status" não comunica que algo está carregando.

Regra dos 15%: estima-se que ~15% da população mundial tem alguma deficiência permanente. Some a isso as deficiências temporárias (braço quebrado, olhos irritados) e situacionais (sol na tela, ambiente barulhento): a maioria das pessoas experimenta barreiras de acessibilidade em algum momento. Construir para acessibilidade é construir para todos.
WCAG 2.1 — os quatro princípios (POUR)

As diretrizes WCAG (Web Content Accessibility Guidelines) organizam os requisitos em quatro princípios. Cada princípio tem critérios de sucesso classificados em três níveis: A (mínimo), AA (recomendado para a maioria dos produtos) e AAA (excelência).

1. Perceptível
A informação deve ser apresentável de múltiplas formas — não depender exclusivamente de uma modalidade sensorial.
  • Texto alternativo para imagens (alt="")
  • Legendas para vídeo e áudio
  • Contraste mínimo 4.5:1 (AA)
  • Conteúdo não depende só de cor
2. Operável
A interface deve ser navegável e operável sem depender de mouse ou gestos de toque.
  • Toda funcionalidade acessível por teclado
  • Focus visível em todos os elementos interativos
  • Sem armadilhas de teclado (keyboard traps)
  • prefers-reduced-motion respeitado
3. Compreensível
O conteúdo e a operação da interface devem ser compreensíveis.
  • Linguagem clara (lang= no html)
  • Labels descritivos em formulários
  • Erros identificados com texto, não só cor
  • Comportamento previsível e consistente
4. Robusto
O conteúdo deve ser robusto o suficiente para ser interpretado por tecnologias assistivas.
  • HTML semântico correto (<button>, <nav>, <main>)
  • ARIA só quando HTML nativo não é suficiente
  • ID únicos na página
  • Status e erros comunicados via ARIA
Contraste de cores — o critério mais violado

O critério 1.4.3 (Contraste Mínimo, nível AA) exige razão de contraste de 4.5:1 para texto normal e 3:1 para texto grande (18pt+ ou 14pt+ negrito). É o critério mais violado em interfaces escuras de IA — textos cinza sobre fundo escuro frequentemente ficam abaixo do limite.

Muted text
1.8:1 ❌ Falha AA
Secondary
3.2:1 ⚠ Falha AA texto
Body text
4.1:1 ⚠ Quase
Primary text
16.8:1 ✅ Passa AAA
Atenção para interfaces dark: textos de categoria "muted" e "secondary" muito comuns em UIs minimalistas costumam falhar o contraste. Use o Chrome DevTools → inspecionar elemento → clicar na cor → ver o "Contrast ratio" para checar cada texto. Toda informação essencial precisa passar 4.5:1.
CSS — prefers-reduced-motion para animações de IA
/* Cursor piscante do chatbot (Semana 7) */
.cursor-blink {
  animation: blink .7s step-end infinite;
}

/* Shimmer do skeleton (Semana 12) */
.skeleton {
  animation: shimmer 1.4s infinite linear;
}

/* Respeitar preferência de movimento reduzido do sistema operacional */
@media (prefers-reduced-motion: reduce) {
  .cursor-blink,
  .skeleton,
  .fade-in,
  .slide-in {
    animation: none;           /* desativa todas as animações */
  }
  .skeleton {
    background: rgba(255,255,255,.07);  /* versão estática do skeleton */
  }
  * {
    transition-duration: 0.01ms !important;  /* minimiza transições CSS */
  }
}
prefers-reduced-motion: ~35% dos usuários de iOS têm "Reduzir movimento" ativado (dados da Apple). Animações contínuas como o shimmer do skeleton e o cursor piscante do chatbot podem causar desconforto em pessoas com epilepsia fotossensível, vertigem ou problemas vestibulares. Sempre envolva animações de IA nessa media query.

ARIA — quando usar e quando não usar

ARIA (Accessible Rich Internet Applications) é um conjunto de atributos que enriquece o HTML com informações semânticas para tecnologias assistivas. A primeira regra do ARIA é: não use ARIA se um elemento HTML nativo resolve. <button> já tem role="button" e é focável — usar uma <div role="button"> exige mais trabalho e mais atributos para equivalência.

Atributo ARIAO que fazUso em chatbot de IA
aria-liveAnuncia mudanças dinâmicas para leitores de telaObrigatório no histórico de mensagens — sem isso, tokens chegando são silenciosos
aria-labelNome acessível para elementos sem texto visívelBotões de emoji (👍), botão de parar stream, textarea do chat
role="status"Região de status — anuncia com pouca interrupçãoSkeleton loader, "Gerando resposta...", contador de tokens
role="alert"Alerta urgente — anuncia imediatamenteErro de API, aviso de contexto longo, rate limit
role="log"Log de mensagens — anuncia adições ao finalÁrea de histórico de conversa do chatbot
aria-busyIndica que uma região está sendo atualizadaContainer das mensagens durante streaming
aria-describedbyAssocia descrição adicional a um elementoInput do chat → aponta para dica "pressione Enter para enviar"
aria-disabledEstado desabilitado (sem retirar do tab order)Botão de enviar durante geração — disabled remove do tab, aria-disabled mantém

Navegação por teclado — foco visível e ordem lógica

Usuários que navegam por teclado (sem mouse) usam Tab para mover entre elementos focáveis, Enter/Space para ativar e Escape para fechar/cancelar. Toda funcionalidade do chatbot deve ser operável dessa forma. O foco visível é obrigatório (WCAG 2.4.7, AA) — remover outline sem substituição é uma violação grave.

Focus invisível — viola WCAG 2.4.7

outline: none — ao pressionar Tab, o usuário não vê onde o foco está.

button:focus { outline: none; } /* ❌ jamais */
Focus visível — passa WCAG 2.4.7

Clique em um botão e pressione Tab para ver o anel de foco. Foco visível e contrastado.

/* :focus-visible mostra só com teclado, não clique */
button:focus-visible {
  outline: 3px solid #2dd4bf;
  outline-offset: 3px;
}
CSS — classe sr-only para texto visualmente oculto mas acessível
/* Oculta visualmente mas mantém para leitores de tela
   Usar para labels de botões de emoji, hints de teclado, etc. */
.sr-only {
  position: absolute;
  width: 1px;
  height: 1px;
  padding: 0;
  margin: -1px;
  overflow: hidden;
  clip: rect(0, 0, 0, 0);
  white-space: nowrap;
  border: 0;
}

/* NÃO usar display:none ou visibility:hidden — remove do acessibility tree */
/* NÃO usar opacity:0 — remove visualmente mas mantém interatividade */
:focus-visible vs :focus: :focus dispara tanto para mouse quanto teclado — o anel aparece ao clicar, o que muitos designers removem por parecer "feio". :focus-visible é mais inteligente: só exibe o indicador quando o usuário navega por teclado (ou quando o browser determina que é necessário). Use sempre :focus-visible nos estilos de foco para a melhor UX.

Exercício 01 — Anunciar progresso de download do modelo

No classificador de imagem da Semana 10, o download do modelo MobileNet (~16MB) mostra uma barra de progresso visual. Para usuários de leitor de tela, a barra SVG é invisível. Adicione uma região aria-live="assertive" que anuncia o progresso a cada 25% (0%, 25%, 50%, 75%, 100% — "Baixando modelo: 50% completo") e um role="progressbar" com aria-valuenow, aria-valuemin e aria-valuemax na barra.

LAB
React — barra de progresso acessível
// Estado: progresso de 0 a 100
const [progresso, setProgresso] = useState(0);
const [anuncio, setAnuncio] = useState('');
const marcosRef = useRef(new Set());

useEffect(() => {
  const marcos = [25, 50, 75, 100];
  marcos.forEach(m => {
    if (progresso >= m && !marcosRef.current.has(m)) {
      marcosRef.current.add(m);
      setAnuncio(`Baixando modelo: ${m}% completo`);
      if (m === 100) setAnuncio('Modelo carregado. Pronto para classificar imagens.');
    }
  });
}, [progresso]);

// No JSX:
<>
  {/* Região de anúncio — visualmente oculta */}
  <div role="status" aria-live="assertive" className="sr-only">
    {anuncio}
  </div>

  {/* Barra visual com semântica ARIA */}
  <div
    role="progressbar"
    aria-valuenow={progresso}
    aria-valuemin={0}
    aria-valuemax={100}
    aria-label="Progresso de download do modelo"
    className="progress-track"
  >
    <div
      className="progress-fill"
      style={{ width: `${progresso}%` }}
    />
  </div>
</>
Exercício 02 — Modal de confirmação acessível

Para o chatbot, implemente um dialog de confirmação que aparece antes de limpar o histórico ("Tem certeza? Esta ação não pode ser desfeita"). O modal deve: (1) ter role="dialog" com aria-modal="true" e aria-labelledby apontando para o título, (2) capturar o foco ao abrir (focus no botão de confirmação), (3) devolver o foco ao botão que o abriu ao fechar, (4) fechar com Escape, (5) impedir Tab de sair do modal (focus trap).

LAB · foco
React — ModalConfirmacao com focus trap
import { useEffect, useRef } from 'react';

function ModalConfirmacao({ onConfirmar, onCancelar, triggerRef }) {
  const confirmarRef = useRef(null);
  const modalRef = useRef(null);

  useEffect(() => {
    // Foco no botão confirmar ao abrir
    confirmarRef.current?.focus();

    // Fechar com Escape
    const onKeyDown = (e) => {
      if (e.key === 'Escape') onCancelar();

      // Focus trap — manter Tab dentro do modal
      if (e.key === 'Tab') {
        const focaveis = modalRef.current.querySelectorAll(
          'button, [href], input, select, textarea, [tabindex]:not([tabindex="-1"])'
        );
        const primeiro = focaveis[0];
        const ultimo = focaveis[focaveis.length - 1];
        if (e.shiftKey && document.activeElement === primeiro) {
          e.preventDefault(); ultimo.focus();
        } else if (!e.shiftKey && document.activeElement === ultimo) {
          e.preventDefault(); primeiro.focus();
        }
      }
    };
    document.addEventListener('keydown', onKeyDown);

    return () => {
      document.removeEventListener('keydown', onKeyDown);
      // Devolver foco ao botão que abriu
      triggerRef.current?.focus();
    };
  }, []);

  return (
    <div className="modal-overlay">
      <div
        ref={modalRef}
        role="dialog"
        aria-modal="true"
        aria-labelledby="modal-titulo"
        className="modal"
      >
        <h2 id="modal-titulo">Limpar histórico?</h2>
        <p>Esta ação não pode ser desfeita.</p>
        <div>
          <button ref={confirmarRef} onClick={onConfirmar}>Confirmar</button>
          <button onClick={onCancelar}>Cancelar</button>
        </div>
      </div>
    </div>
  );
}
Exercício 03 — Modo alto contraste com prefers-contrast

A media query @media (prefers-contrast: more) detecta quando o sistema do usuário está configurado para alto contraste (comum em usuários com baixa visão). Adicione ao seu chatbot um conjunto de overrides CSS que: (1) aumenta contraste de todos os textos para 7:1+, (2) adiciona bordas visíveis em elementos interativos, (3) remove backgrounds semi-transparentes substituindo por sólidos, (4) aumenta o anel de foco para 4px. Teste ativando "Increase Contrast" no macOS.

CSS
CSS — overrides para alto contraste
@media (prefers-contrast: more) {
  /* Texto — forçar máximo contraste */
  .text-secondary, .text-muted,
  [style*="rgba(255,255,255"] {
    color: rgba(255,255,255,.95) !important;
  }

  /* Backgrounds — remover transparência */
  .card, .bubble, .questao {
    background: #111 !important;
    border-color: rgba(255,255,255,.5) !important;
    border-width: 2px !important;
  }

  /* Botões — mais visíveis */
  button {
    border: 2px solid currentColor !important;
  }

  /* Foco — mais grosso */
  *:focus-visible {
    outline-width: 4px !important;
    outline-color: #fff !important;
  }

  /* Skeleton — versão sólida */
  .skeleton {
    background: #333 !important;
    animation: none !important;
  }

  /* Links — underline sempre visível */
  a { text-decoration: underline !important; }
}

aria-live="polite" no histórico. role="status" no skeleton. role="alert" nos erros. aria-label nos botões de emoji. aria-pressed nos toggles. aria-describedby no textarea.

Auditoria e correção

axe DevTools + Lighthouse para automático. Tab + leitor de tela para manual. sr-only para texto oculto. :focus-visible para anel de foco. prefers-reduced-motion para animações.

Checklist final: o score Lighthouse Accessibility está ≥ 90? O axe não encontra violações críticas? Navegar com Tab percorre todos os elementos interativos em ordem lógica com foco visível?
